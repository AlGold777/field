# Оценка результата DeepSeek StereoSplit

Дата: 27 октября 2026, Europe/Madrid. Основание: поручение руководить исследованием и оценить, открывает ли результат путь к исходной задумке.

## Решение

**Продолжать ограниченную проверку осуществимости. Не считать concurrency или весь продукт доказанными.**

Положительный результат пока узкий: в сохранённых логах Xiaomi 24030PN60G, Android 16/API 36, JBL Clip 4 сообщает разные маршруты для MEDIA→BT и ALARM→speaker. Это полезный кандидат для проверки. Если физически независимый одновременный вывод подтвердится, будет снят один существенный барьер на этой конфигурации. Захват Spotify, подавление оригинала и синхронизация останутся самостоятельными условиями.

Провал текущего прототипа тоже не доказывает аппаратную невозможность: найдены дефекты эксперимента и реализации.

## Дефекты доказательства и кода

1. **Старый PASS проверяет маршруты.** `DualRoutingProbe.kt:335–353`: последовательные blocking write, ожидание и сравнение типов `routedDevice`. Отдельного измерения временного перекрытия звука нет. Попеременное звучание могло зависеть от самого теста; делать вывод о мультиплексировании HAL по этому наблюдению нельзя.
2. **Новый continuous PASS тоже переутверждает результат.** `DualRoutingProbe.kt:248–262`: успех определяется отсутствием совпадения типов и двумя `PLAYSTATE_PLAYING`. Null-маршруты не вызывают отказа; ошибки/короткие записи не участвуют в вердикте. Акустической проверки нет. На API 36 дополнительно следует собирать `getRoutedDevices()`: один сообщённый маршрут недостаточен для проверки отсутствия дублирования на другой выход.
3. **Сигналы continuous-зонда не являются чистыми непрерывными синусами.** `DualRoutingProbe.kt:198–219`: повторяется массив из 480 отсчётов при 48 кГц, то есть 4,4 периода 440 Гц или 8,8 периода 880 Гц. Фаза сбрасывается на границе блока. Для измерений нужна непрерывная фаза и различимые тестовые последовательности; 880 Гц также совпадает со второй гармоникой 440 Гц и затрудняет оценку утечки.
4. **Гонка запуска левого выхода.** `DualTrackRenderer.kt:33,105,125,197`: левый feeder стартует при `isRunning=false`; true устанавливается после построения и запуска правого трека. Поток может выйти до первой записи. Дефект установлен статически; его участие в конкретном полевом сбое не доказано.
5. **Mute не избирателен.** `AudioSplitService.kt:269–299` меняет общий `STREAM_MUSIC`; `DualTrackRenderer.kt:57–60` создаёт собственный BT-трек с `USAGE_MEDIA`. Нулевая громкость/глушение затрагивает этот выход вместе с оригиналом. Индекс 1 не доказывает ни тишину оригинала, ни независимую громкость полезного канала. Absolute Volume может дополнительно менять громкость приёмника, но выключение усилителя JBL из доступных материалов не установлено.
6. **RMS не идентифицирует Spotify.** `AudioCaptureManager.kt:63–68` захватывает допустимые usages всех чужих UID, исключая свой. Для доказательства нужен UID Spotify либо строгая изоляция источников с проверкой play/pause и содержимого PCM. Тишина сама по себе не доказывает DRM/offload.
7. **Синхронизация не измеряется.** В локальной ветви применяется заданная задержка R; класс `ClockDriftCompensator` не имеет вызовов. Возраст timestamp `AudioRecord` не равен разнице акустических задержек двух выходов. Выравнивание L/R не гарантирует совпадения звука с видео стороннего приложения.
8. **Молчание журнала не локализует ошибку.** `AudioSplitService.kt:381–389`: heartbeat запускается лишь после старта capture. Зависание раньше этого места не будет видно heartbeat. Последнее сообщение UI об отправке команды запуска ещё не доказывает вход в сервис.

## Порядок дальнейших экспериментов

До полевых испытаний: зафиксировать точный исходный код/APK, устранить гонку подачи, исправить генератор и критерии вердикта. Ввести раздельные состояния «маршруты сообщены», «данные записываются», «слышимость подтверждена», «синхронизация измерена». Проверки кода делегировать GPT-6 Luna high. Это план, изменения реализации в рамках данной оценки не выполнялись.

1. **Два физических выхода.** Без Spotify и mute, безопасный фиксированный уровень, M/S выключен. Непрерывные разные сигналы в течение 30 секунд с отметками маршрутов, количества успешно записанных кадров и ошибок. Проверить, что одновременно слышны разные сигналы из назначенных устройств; отдельно программно занулять каждый канал, не меняя общий stream volume, чтобы выявить дублирование. Повторить запуск три раза. Слуховая проверка — предварительная, не измерение точной задержки. Если автоматическая запись возможна встроенным микрофоном этого же телефона, предусмотреть контроль акустического проникновения звука; иначе физический результат остаётся пользовательским наблюдением, а не инструментальным доказательством. Не вводить обязательные внешние устройства в исходный инвариант.
2. **Захват Spotify отдельно.** Отключить повторное воспроизведение и mute. Проверить поступление PCM, привязку к Spotify, реакцию на play/pause и содержимое каналов. Подмена источника локальным файлом допустима лишь как контроль исправности capture-тракта и не закрывает условие Spotify.
3. **Совместимость mute с полезными выходами — решающий барьер.** На одном и том же тракте одновременно показать: Spotify продолжает играть и захватываться; исходный стереосигнал перестаёт звучать; собственные L и R остаются слышимыми с независимым содержимым. Поочерёдно занулять собственные выходы, сохраняя состояние остальных частей, для поиска остатка оригинала. Уровень 1 без проверки утечки не принимается за mute. Если способа пройти этот этап нет, успешная concurrency ещё не открывает путь к исходной архитектуре.
4. **Сквозное разделение и время.** Только после предыдущих этапов: штатный Spotify, M/S=0, чистое L/R, несколько минут работы, перезапуски и переподключение. Измерить начальный сдвиг, изменение сдвига и разрывы; затем отдельно измерить audio/video для реального видеосценария. До измерений определить критерии качества. Одна задержка 200 мс и отсутствие слышимого эха не доказывают устойчивую стереосцену или A/V-sync.

Не распространять успех на все Android. Для продукта либо фиксируется список подтверждённых моделей/версий, либо отдельно проверяется переносимость. Глобальное отсутствие гребенчатой фильтрации во всей комнате не является достижимым следствием одной цифровой задержки: различие акустических путей зависит от места слушателя.

## Документальные опоры

- [Android: Capture video and audio playback](https://developer.android.com/media/platform/av-capture): API копирует звук; capture зависит от политики источника; API не изменяет задержку приложения-источника. Это не перехват с автоматическим глушением оригинала и не управление временной шкалой видео.
- [Android: AudioRouting](https://developer.android.com/reference/android/media/AudioRouting): preferred route не гарантирует фактический выход; текущие маршруты доступны при воспроизведении, `getRoutedDevices()` добавлен в API 36. Эти данные полезны, но не заменяют акустическое измерение.
- [Android: Handling changes in audio output](https://developer.android.com/media/platform/output): громкость потока общая для приложений, использующих этот тип потока.
- [AOSP: Bluetooth services — Absolute volume](https://source.android.com/docs/core/connect/bluetooth/services): источник может передавать приёмнику информацию о громкости. Это объясняет возможную связь управления громкостью, но не доказывает конкретный режим усилителя JBL.
- [AOSP: Combined audio device routing](https://source.android.com/docs/core/audio/combined-audio-routing): многовыходная маршрутизация существует в Android; описанные средства выбора нескольких устройств для стратегии предназначены для привилегированных приложений. Нельзя заключать ни универсальную невозможность, ни доступность всех возможностей обычному APK.

## Условие пересмотра решения

Подтверждение этапа 1 повышает статус до «важный частный результат по маршрутизации». Успешное совместное прохождение этапов 1–3 на штатном Spotify открывает обоснованный путь к прототипу исходной задумки. Только этап 4 и воспроизводимость позволяют обсуждать пригодность результата для пользователя. Сейчас корректный статус — **перспективный маршрут, требующий решающего эксперимента**.
