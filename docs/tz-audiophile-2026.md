# ТЗ: аудиофильский тракт SoundField (программа A, октябрь 2026)

**Исполнитель:** Claude Sonnet 5.5 (ведущий этапа) + субагенты Claude Haiku 5.5 (механические части).
**База:** Android 1.10.30 (68), iOS 1.3.12 (31), протокол v2 (HMAC-теги, защита от повтора).
**Автор ТЗ:** Claude Opus 5.5, 2026-10-22.

---

## 0. Цель и рамки

Цель — максимально достижимое качество звука пары из двух телефонов (и одного телефона в Solo) при физических пределах их динамиков. Качество определяется измеримыми величинами (§2), а не наличием функций.

Принципы, обязательные для всех этапов:

1. **Пользователь только слушает.** Никаких новых настроек, тестов, подтверждений, подсказок и экранов в обычном UI. Всё определяется автоматически (модель телефона, громкость, маршрут), при неизвестности — безопасное значение по умолчанию. Инструменты измерений — только в скрытом режиме разработчика и в `tools/`.
2. **Ровно два источника звука** (два телефона или стереотелефон в Solo). Никаких сабвуферов, N-устройств, объектного рендеринга.
3. **Переносимость.** Алгоритмы не зависят от телефона: устройство описывается профилем (§A2), DSP — в общем ядре (§1), которое переносится на будущие устройства без изменений.
4. **Честность метрик.** Каждое утверждение о качестве подтверждается числом из лаборатории (§A0.3) или замером на устройстве. Нельзя улучшать «на слух» без метрики. Каждое изменение публикует таблицу «до/после».
5. **Обработка не должна ухудшать исходник там, где динамик его может воспроизвести.** Компрессия динамики, окрашивание и «улучшайзеры» запрещены, кроме случаев, когда они компенсируют конкретный физический предел динамика (низкочастотный срез, ход диффузора, равногромкость).

Не входит в программу A: сжатый стриминг сторонних сервисов, захват системного звука, сабвуфер, многоканальность, видео-синхронизация.

## 1. Архитектура: общее DSP-ядро `sfdsp`

### 1.1 Решение

Весь **новый** DSP пишется один раз на **C++20** в каталоге `dsp/` с **C ABI** (`dsp/include/sfdsp.h`). Kotlin вызывает его через JNI (`android/.../dsp/SfDsp.kt`, тонкая обёртка), Swift — через bridging header (чистый C, без C++-interop Swift). Существующий Kotlin-DSP (EQ, spatial, `PlayoutCorrector`, `WindowedSinc`) переносится в ядро по этапам; до переноса Kotlin- и C++-реализации сверяются тестами на одинаковых входах (расхождение ≤ −120 dB относительно сигнала).

Причина: двойная реализация на Kotlin и Swift уже разошлась (iOS не имеет дробного корректора, EQ, spatial); одно ядро даёт бит-в-бит одинаковый звук на обеих платформах и тестируется на Mac без телефона.

### 1.2 Правила реального времени (обязательны для кода, вызываемого из аудиопотока)

- Без выделения памяти, блокировок, системных вызовов, логирования, исключений. Вся память — в `create()`.
- Параметры меняются через двойной буфер с атомарной публикацией указателя (`std::atomic<const Params*>`), применяются на границе блока; все «слышимые» параметры интерполируются (рампа ≥ 10 мс, для фильтров — интерполяция коэффициентов в домене параметров или кроссфейд двух экземпляров).
- Денормалы: FTZ/DAZ на входе в `process()` (ARM64: бит FZ в FPCR; x86: MXCSR), восстановление на выходе.
- Внутренняя арифметика — `float32`; накопители длинных FIR, IIR-состояния низких частот и SRC — `double`.
- Блок произвольного размера 1…4096 кадров; поведение не зависит от размера блока (тест: одинаковый выход при блоках 1, 37, 240, 4096).
- Каждая цепочка сообщает `latency_frames()`; **разница задержек цепочек двух телефонов компенсируется во временной шкале** (Server и Point вычитают свою задержку цепочки из времени предъявления). Тест: импульс через цепочки двух разных профилей приходит в один кадр общей шкалы.

### 1.3 Цепочка обработки (целевая)

```
Источник (файл, любой SR/разрядность)
 └─ импорт: декод → SRC к 48 кГц (A1.2) → кэш float32/24 бит → анализ громкости BS.1770 (A3.1)
Server, общая часть (оба канала, стерео-сцепленная):
 └─ нормализация громкости трека (A3.1) → сцена: ширина/XTC Solo (A6) → сцепленный предлимитер −1,5 dBTP (A1.4)
 └─ разделение каналов: свой канал → локальная цепочка; второй канал → сеть 24 бит (A1.3, A4)
Цепочка устройства (на каждом телефоне, по его профилю):
 └─ позиционная коррекция пары (A5) → равногромкость (A3.2) → виртуальный бас (A3.3)
 └─ коррекция динамика (A2) → защита хода диффузора (A3.4) → true-peak лимитер −1,0 dBTP (A1.4)
 └─ дробный корректор синхронизации (A4.1) → вывод float в AudioTrack / AVAudioEngine
```

### 1.4 Версии

`dsp/include/sfdsp_version.h`: `SFDSP_VERSION` (semver), повышается при любом изменении звука ядра; отображается в диагностике и пишется в телеметрию вместе с версией таблицы профилей `PROFILES_VERSION`. Версии приложений — как раньше (versionName/versionCode, MARKETING_VERSION/CURRENT_PROJECT_VERSION).

Порядок обязателен: A0 → A1 → A2 → A3 → A4 → A5 → A6 → A7. A2 частично параллелен A1 (измерения не блокируют код). ### A0. Инфраструктура ядра и лаборатории

**A0.1 Ядро.** `dsp/CMakeLists.txt`, `dsp/include/sfdsp.h`, `dsp/src/*.cpp`, `dsp/tests/*.cpp` (собственный минимальный тест-раннер, без внешних библиотек). Первый блок для проверки сборки — перенос `WindowedSinc` + `PlayoutCorrector` Android (32 отвода Kaiser, 256 фаз, PI-регулятор) с тестом совпадения с Kotlin (§1.1).

**A0.2 Сборка на платформах.**
- Android: установить Android SDK command-line tools и NDK r27 LTS + CMake 3.22 через `sdkmanager` (загрузка с dl.google.com — официальный источник; записать точные версии в `android/README-native.md`). `externalNativeBuild` в `android/app/build.gradle.kts`, ABI `arm64-v8a` (+ `armeabi-v7a`, если minSdk-устройства этого требуют — проверить по списку тестовых телефонов). Для JUnit на JVM — хост-сборка той же библиотеки (`dsp/` → `libsfdsp.dylib` для macOS), загружаемая тестами через `System.load`.
- iOS: `dsp/src/*.cpp` и `dsp/include` в target через `ios/project.yml` и `tools/gen_xcodeproj.py`; bridging header `ios/SoundField/SoundField-Bridging-Header.h`. Расширить `tools/ios_typecheck.sh`: компиляция C++ под `arm64-apple-ios16.0-macabi` (`clang++ -std=c++20`, проверено: работает с CLT) + `-import-objc-header` для Swift.
- Скрипт `tools/dsp_check.sh`: сборка ядра на Mac, тесты ядра, `sflab`, сравнение с базовой линией. Должен проходить без телефона и без Xcode.

**A0.3 Лаборатория `sflab`** (`dsp/lab/`, хост-бинарник). Прогоняет любую цепочку ядра (и, через хост-JNI-мост, текущий Kotlin-рендер) по набору сигналов и выдаёт JSON:
- синусы (20 Гц–20 кГц, −1/−20/−60 dBFS) → THD+N, гармоники H2–H5, шумовая полка;
- экспоненциальный свип (ESS, метод Фарины) → АЧХ, фазовая/групповая задержка, гармоники по частоте;
- двухтоновые тесты IMD (SMPTE 60 Гц + 7 кГц 4:1, CCIF 19+20 кГц);
- null-тест; true-peak (4× oversampling); межсэмпловые пики на «опасных» сигналах (fs/4 со сдвигом фазы 45°);
- синхронизация: две цепочки с моделью часов (дрейф, джиттер, асимметрия, потери) → ошибка L/R во времени;
- музыкальный корпус: `tools/audio-corpus/` — 10–15 фрагментов по 20 с с открытой лицензией (CC0/CC-BY, источник и лицензия в `tools/audio-corpus/LICENSES.md`), разные жанры, есть хотя бы один с глубоким басом, один акустический, один плотно сведённый, один моно.
Базовая линия `dsp/lab/baseline.json`; регрессия любой метрики сверх допуска — провал `dsp_check.sh`.

**Приёмка A0:** ядро собирается на Mac, Android (APK содержит `libsfdsp.so`), проходит `ios_typecheck.sh`; перенесённый `PlayoutCorrector` совпадает с Kotlin ≤ −120 dB; `sflab` выдаёт метрики **текущего** тракта (Android и iOS-эквивалент через ядро) — это базовая линия программы. Звук приложения на этом этапе не меняется.

**Делегирование Haiku:** CMake/Gradle/project.yml-обвязка по точной инструкции; генераторы тестовых сигналов; сбор корпуса (поиск CC0-треков с проверкой лицензии — только записать кандидатов, финальный выбор — Sonnet).

### A1. Целостность сигнального тракта

**A1.1 Разрядность.** Внутренний тракт — float32. Кэш декодированного трека — 24 бит packed (или float32, если исходник float); PCM16-кэш упраздняется (миграция: старый кэш перекодируется при следующем открытии). iOS: декод через `AVAudioFile` в float32 без промежуточного Int16. Квантование до 24 бит — с TPDF-дизерингом (2 независимых равномерных значения по ±0,5 LSB, генератор xorshift128+, свой на канал).

**A1.2 SRC.** Полифазный оконный sinc (окно Kaiser), коэффициенты считаются при импорте. Требования: полоса пропускания до 20 кГц с неравномерностью ≤ ±0,01 dB, подавление ≥ 120 dB, начало подавления — на min(fs_in, fs_out)/2. Ориентир: Δf = 2,05 кГц при 44,1 кГц → порядка 170 отводов на фазу; Kaiser β ≈ 12. Накопление в double. Выполняется при импорте (не в реальном времени), поэтому стоимость не ограничена бюджетом блока, но импорт трека 4 мин на Redmi 14C ≤ 10 с. Тот же SRC — на iOS (вместо `AVAudioConverter`) и для встроенного WAV (вместо линейной интерполяции).

**A1.3 Сеть 24 бит.** Аудиопакет Point: PCM 24 бит, **384 кадра** (8 мс) на пакет: 1152 байта PCM + заголовок + HMAC-тег ≤ 1232 байт UDP-полезной нагрузки — гарантированно без IP-фрагментации и для IPv6 (минимальный MTU 1280). Новая версия протокола `PROTOCOL_VERSION = 3`, отказ v2 через существующий `reject: proto`. Обновить `Wire.kt`/`Wire.swift` (или вынести кодек пакета в ядро — предпочтительно), `tools/protocol_vectors.json`, `WireVectorsTest`, `tools/check_protocol_vectors.swift`, README «Протокол». TCP-аудио (`TcpAudio`) — тоже 24 бит.

**A1.4 Пиковое управление.**
- Сцепленный предлимитер на Server до разделения каналов: порог −1,5 dBTP, lookahead 1,5 мс, детектор true-peak (полифазный 4× по BS.1770-4 Annex 2, 48 отводов), атака — минимум по окну lookahead со сглаживанием окном Ханна, восстановление двухпостоянное (быстрое 50 мс для единичных пиков, медленное 400 мс при частых), общее усиление для L и R (стереокартина не смещается).
- Финальный лимитер устройства: −1,0 dBTP, та же конструкция; в нормальной работе срабатывает редко (метрика в телеметрии: доля блоков с ослаблением > 0,5 dB; цель < 1% на корпусе при максимальной громкости).
- Существующие лимитеры Android (EQ limiter, `SpatialPeakLimiter`) заменяются этими двумя; двух лимитеров подряд с разными постоянными быть не должно.

**A1.5 Громкость.** Сначала измерить в `sflab` и на устройствах (шумовая полка при цифровом ослаблении −30 dB против системной громкости). Если разница в шуме на выходе DAC/усилителя телефона не выявляется измерением (ожидаемо — float до микшера ОС), закон громкости не меняется; результат записать в `docs/audio-algorithms.md`. Не вводить управление системной громкостью без измеренной пользы.

**Приёмка A1:** метрики §2 «null», «THD+N», «шумовая полка», «SRC», «true-peak» выполнены; корпус через новый тракт: изменение интегральной громкости ≤ 0,1 LU при выключенных предлимитере/лимитере; протокол v3 проходит векторы на обеих платформах.

**Делегирование Haiku:** обновление векторов и тестов протокола, порт вызовов в `Engine.swift`, миграция кэша (по готовому формату), README.

### A2. Профили устройств и коррекция динамиков

Самый слышимый этап. Разделён на измерение (A2.1–A2.2, нужен измерительный микрофон) и код (A2.3–A2.6, можно делать параллельно на синтетических профилях).

**A2.1 Стенд (одноразовый, выполняет разработчик).**
- Измерительный USB-микрофон с индивидуальным калибровочным файлом (класс miniDSP UMIK-1/UMIK-2) на Mac; тихое помещение; телефон на подставке экраном к слушателю в рабочем положении пары.
- Точки: 1 м на оси, 1 м под ±30° по горизонтали; ближнее поле 1–2 см от каждого излучателя для НЧ.
- Сигнал: ESS 20 Гц–24 кГц, 2^18 отсчётов, уровни −30, −20, −12, −6, −3, 0 dBFS при **максимальной системной громкости** и при 3 промежуточных шагах громкости (для таблицы чувствительности).
- Воспроизведение: скрытый режим разработчика «Lab» в приложении принимает с Mac команду (HTTP на localhost-туннеле через `adb reverse` для Android, через существующий TCP-канал разработчика или файл в приложении — выбрать простейший) и проигрывает свип **через полный выходной путь приложения** с выключенной обработкой ядра; Mac записывает и находит свип корреляцией.
- Инструмент: `tools/speaker-lab/` (Python 3 + numpy/scipy в venv `tools/speaker-lab/.venv`, зависимости в `requirements.txt` с версиями) — деконволюция ESS, разделение гармоник, окно 3–5 мс для квазибезэховой АЧХ выше ~300 Гц, сшивка с ближним полем ниже.

**A2.2 Профиль** (`profiles/devices.json`, общий для Android и iOS, `PROFILES_VERSION`):
```
model_keys: [Build.MANUFACTURER/MODEL/DEVICE | iOS hw.machine]
modes: { pair_mono: {...}, solo_stereo: { left: {...}, right: {...}, spacing_m } }
для каждого излучателя/режима:
  fr_db[]            — АЧХ на сетке 1/48 окт. 20 Гц–24 кГц: 0°, ±30°, среднее
  sens_db_spl_1m     — SPL на 1 м при 0 dBFS (розовый шум) для каждого шага громкости
  f_low_hz           — нижняя граница (−6 dB от среднего уровня 500 Гц–5 кГц)
  max_level_dbfs[f]  — уровень, при котором THD = 3% (по частотам 1/3 окт.)
  compress_onset_db  — уровень начала аппаратной компрессии (по отклонению от линейности ≥ 0,5 dB)
  f0_hz, q0          — оценка резонанса излучателя (из НЧ-подъёма АЧХ/фазы ближнего поля)
  output_bias_us     — систематическая ошибка заявленного ОС момента вывода (из A4.4)
  os_effects         — состояние системных эффектов при измерении (Dolby/фирменные улучшатели), отпечаток
  correction         — результат A2.3 (биквады, allpass), генерируется инструментом, не пишется руками
```
Первые профили: Xiaomi 14 Ultra, Redmi 14C, тестовый iPhone. Неизвестная модель → класс `generic_phone_speaker`: только ФВЧ по 250 Гц, без подъёмов (не хуже текущего).

**A2.3 Синтез коррекции (в `tools/speaker-lab/`, результат — в профиль).**
- Цель T(f): ровная в 300 Гц–8 кГц для среднего (0° и ±30° с весами 0,5/0,25/0,25), выше 8 кГц наклон −1 dB/окт.; ниже `f_low` цель следует за динамиком (низы — задача A3.3, не коррекции).
- Ошибка сглаживается: 1/6 окт. до 1 кГц, переход к 1/3 окт. к 10 кГц (сглаживание по ERB-плотности).
- Ограничения: подъём ≤ +6 dB (≤ +3 dB выше 8 кГц), срез ≤ −15 dB, узкие провалы (< 1/3 окт., признак неминимальнофазовости/интерференции) не поднимаются.
- Аппроксимация: каскад минимально-фазовых биквадов (до 14 пиковых + 2 полочных, Q ≤ 6), оптимизация логарифмической ошибки с весом по ERB (инициализация жадная, уточнение Левенберга–Марквардта). Предусиление ядра = −max(подъём) — запас под A1.4.
- **Согласование пары:** оба телефона приводятся к одной T. Затем по измеренным фазам (после удаления общей задержки и минимально-фазовой части) считается разность групповой задержки излучателей двух моделей в 500 Гц–4 кГц; если > 20 мкс, для опережающего телефона синтезируется allpass (до 4 секций второго порядка), сводящий разность ≤ 20 мкс. Это касается **пары конкретных моделей**: allpass хранится в профиле как функция «модель партнёра» → секции, вычисляется при `build` таблицы для всех пар известных моделей.

**A2.4 Ядро:** блок `speaker_correction` (биквады в форме TDF-II, double-состояние ниже 200 Гц; allpass), загрузка профиля по ключу модели, плавная смена профиля (кроссфейд 50 мс) при смене партнёра/режима.

**A2.5 Автоопределение.** Android: `Build.MANUFACTURER`, `MODEL`, `DEVICE`; iOS: `utsname.machine`. Маршрут — только встроенный динамик: при наушниках/Bluetooth коррекция динамика выключается (профили для внешних устройств вне программы A). Телеметрия: ключ модели, найден ли профиль, `PROFILES_VERSION`.

**A2.6 Системные эффекты ОС.** Определить, что доступно без root: Android — `AudioEffect.queryEffects()`, известные системные настройки Dolby/фирменных улучшателей, если читаются; iOS — не применимо. Если отпечаток при воспроизведении отличается от `os_effects` профиля — использовать коррекцию с ограничением подъёмов до +2 dB и записать событие в телеметрию. Пользователю ничего не показывать.

**Приёмка A2:** на каждом профилированном телефоне повторный замер с коррекцией: отклонение от T ≤ ±1,5 dB (300 Гц–8 кГц, 1/6 окт., среднее 0°/±30°); пара 14 Ultra + 14C: разность АЧХ L/R ≤ ±1 dB, разность групповой задержки ≤ 20 мкс (500 Гц–4 кГц); `sflab`: блок не нарушает null/THD+N-бюджеты при плоском профиле.

**Делегирование Haiku:** парсинг/валидация `devices.json` (схема + тест), Swift/Kotlin-загрузка профиля, сбор телеметрии; инструмент измерений и синтез — Sonnet.

### A3. Громко и чисто на маленьком динамике

**A3.1 Нормализация громкости трека.** При импорте — интегральная громкость BS.1770-4 (K-взвешивание, стробирование −70 LUFS абсолютное, −10 LU относительное) и true-peak; хранить в метаданных очереди. Воспроизведение: усиление = −16 LUFS − L_трека, при подряд идущих треках одного альбома (теги album/albumartist) — альбомное значение. Усиление ограничено так, чтобы true-peak после него ≤ −1,5 dBTP, иначе остаток отдаётся предлимитеру (A1.4) только если превышение ≤ 3 dB, при большем — усиление уменьшается (не пережимать громкие мастеринги ради тихих).

**A3.2 Равногромкостная компенсация.** Оценка уровня у слушателя: `SPL ≈ sens_db_spl_1m(шаг громкости) + цифровое усиление + (−16 − (−20)) − 20·lg(d/1 м)`, d = 1,5 м в паре, 0,5 м в Solo. Компенсация = разность контуров ISO 226:2023 между 80 phon и текущим уровнем, аппроксимированная низкой полкой (частота и наклон подбираются под разность контуров в диапазоне `f_low`…500 Гц) и высокой полкой (> 8 кГц); ограничения +6 dB НЧ (дополнительно ограничивается A3.4) и +3 dB ВЧ; изменение параметров со сглаживанием 300 мс. Таблица контуров — в ядре, интерполяция по phon.

**A3.3 Виртуальный бас (новый алгоритм ядра).** Задача: передать ощущение частот ниже `f_low` через их гармоники, не вызывая интермодуляции на многоголосом басе.
1. Разделение кроссовером Линквица–Райли 4-го порядка на `fc = f_low` (из профиля): НЧ-полоса удаляется из прямого пути, сумма полос фазово-согласована.
2. НЧ-полоса делится на 3 субполосы по октавам ниже fc (LR4), чтобы ноты в разных субполосах не интермодулировали.
3. В каждой субполосе — генератор гармоник на **полиномах Чебышёва**: сигнал нормируется на огибающую (быстрая атака 1 мс, отпускание 30 мс; детектор — модуль аналитического сигнала через КИХ-преобразователь Гильберта), к нормированному сигналу u применяется Σ wₖ·Tₖ(u), k = 2…5. Для синусоиды Tₖ даёт ровно k-ю гармонику без продуктов, нормировка делает спектр гармоник независимым от уровня; затем умножение обратно на огибающую.
4. Веса wₖ подбираются офлайн (A0.3 + слуховой отбор в скрытом режиме) так, чтобы воспринимаемая громкость гармоник по упрощённой модели громкости Мура–Гласберга равнялась громкости удалённой основной; результат — таблица по fc.
5. Гармоники ограничиваются полосой [fc, 4·fc] (LR4) и складываются с прямым путём; задержка выравнивается.
6. Две реализации: «качество» (описанная) и «экономная» (одна субполоса, k = 2…3) для CPU-деградации (§2).
Приёмка: энергия ниже fc на выходе ≤ −20 dB относительно входа (снятие хода диффузора); двухтоновый басовый тест (41 + 55 Гц, ноты в разных субполосах) — разностные продукты ≤ −30 dB относительно гармоник; громкость фрагментов корпуса с басом в пределах ±1 LU относительно версии без обработки на «идеальном широкополосном динамике»; задержка ≤ 3 мс.

**A3.4 Защита хода диффузора (вместо широкополосной компрессии).**
- Модель хода: x(t) — сигнал после коррекции динамика, пропущенный через ФНЧ 2-го порядка с f0, q0 из профиля (ход микродинамика в закрытом объёме пропорционален этой передаточной функции). Порог x_lim — значение модели при уровне `max_level_dbfs` в районе f0.
- Упреждение 3 мс: если пик предсказанного хода превышает x_lim, плавно повышается частота динамического ФВЧ 2-го порядка (а не общий уровень), до требуемого снижения хода; возврат 200 мс. Снятые низы компенсирует A3.3 (связь: тот же fc-сдвиг подаётся генератору гармоник).
- Порог дополнительно держит уровень ниже `compress_onset_db`, чтобы не включался аппаратный защитный усилитель телефона (его «накачка» хуже нашей прогнозируемой обработки).
Приёмка: на корпусе при максимальной громкости — THD на НЧ-сигналах у излучателя (лабораторный замер) не выше 3%, общий уровень (LUFS) не ниже версии A2 более чем на 1 LU; при громкости ≤ 50% блок неактивен.

**Запрещено:** многополосная компрессия динамики «для громкости», обострение транзиентов, «экскайтеры» ВЧ.

**Делегирование Haiku:** BS.1770-анализатор по готовой спецификации (+ тест на эталонных сигналах EBU Tech 3341), таблицы ISO 226:2023, хранение метаданных громкости в очереди обеих платформ.

### A4. Синхронизация и транспорт

**A4.1 Дробный корректор в ядре** (перенос из A0.1 в работу на обеих платформах). iOS получает дробную коррекцию вместо ±1 отсчёта. Приёмка: THD+N синуса 1 кГц через корректор при дрейфе 50 ppm ≤ −110 dB; цифровая ошибка L/R при ±100 ppm и джиттере — p95 ≤ 10 мкс.

**A4.2 Модель часов — фильтр Калмана** (состояние: смещение, дрейф; ядро, общее для платформ). Измерения: минимумы по корзинам 0,5 с от PING/PONG и односторонних меток аудиопакетов; шум измерения — из разброса RTT в корзине; шум процесса — по уходу кварца (порядка 1e-9 с/с²). Асимметрия: верхняя граница погрешности = половина минимального RTT (уже в коде) сохраняется как отдельная величина. Замена текущей регрессии только если `sflab` на одинаковых трассах (включая записанные трассы телеметрии реальных устройств) даёт меньшую ошибку p95; иначе остаётся текущая.

**A4.3 Восстановление пропусков (вместо тишины).** Point держит ~400 мс будущих данных, поэтому пропуск обычно окружён данными с обеих сторон:
- двунаправленная интерполяция: LPC порядка 32 по 20 мс до пропуска (прямой прогноз) и после (обратный прогноз), смешивание с окном raised-cosine по длине пропуска; для пропусков > 40 мс — прогноз с затуханием до нуля за 20 мс и плавный вход;
- выполняется в сетевом потоке Point при окончательной потере пакета (350 мс), не в аудиопотоке.
Приёмка: корпус со случайными пропусками 8–40 мс — сегментный SNR восстановленного участка ≥ 10 dB в среднем, ноль разрывов производной сверх порога.

**A4.4 FEC и упаковка.**
- XOR-паритет на группу из 4 пакетов, включается автоматически при потерях > 0,5% за 10 с, выключается при < 0,1% за 60 с. Восстанавливает одиночную потерю без NACK.
- Сжатие без потерь (опционально, решение по телеметрии потерь): фиксированные предсказатели порядка 0–4 на пакет + код Райса, как в FLAC; цель — 50–60% объёма 24-бит PCM; включается при доле потерь > 0,5%.
- Плавная отправка: пакеты на равномерной сетке, без пачек.

**A4.5 Калибровка задержки v2.** ESS в полосе излучателя (300 Гц–16 кГц, из профиля), взаимная корреляция с весом PHAT (GCC-PHAT) — устойчива к реверберации; прямой путь — правило уже реализовано (первый ≥ 50% максимума + главный лепесток 1 мс); уточнение — по наклону фазы взаимного спектра в 1–6 кГц (оценка групповой задержки), а не параболой. 6 повторов, медиана/MAD. Цель — повторяемость ≤ 10 мкс (MAD). Та же запись используется в A5. Звучание калибровки и её запуск в UI — как сейчас (кнопка пользователя), без новых экранов.

**A4.6 Смещение момента вывода по модели.** В лаборатории (UMIK у обоих телефонов, один и тот же свип с общей шкалой) измерить систематическую ошибку «заявленный ОС момент вывода → реальный звук» для каждой модели и маршрута; записать в профиль `output_bias_us` и вычитать во временной шкале. Это делает пару правильной **до** пользовательской калибровки.

**Приёмка A4:** акустический замер пары (два телефона, UMIK посередине на 1 м): p95 ≤ 50 мкс (цель 20 мкс) за 10 мин воспроизведения без калибровки пользователя, только по A4.6; с калибровкой v2 — p95 ≤ 20 мкс.

**Делегирование Haiku:** порт FEC/упаковки на Swift при выносе кодека пакета в ядро — не нужен (ядро общее); тесты кодека, векторы протокола, телеметрия потерь/FEC.

### A5. Позиционная коррекция пары (в точке слушателя)

Использует запись калибровки v2 (A4.5): Server находится у слушателя, его микрофон записывает свипы обоих телефонов.
- Для каждого телефона — импульс деконволюцией ESS, окно 5 мс (прямой звук + ранние отражения), АЧХ 300 Гц–12 кГц, сглаживание 1/3 окт.
- **Сравнивается только L против R**: характеристика микрофона одинакова для обоих и сокращается, калибровка микрофона не требуется. Коррекция приводит оба канала к их среднему: ±3 dB максимум, низкодобротные полки/пики (≤ 6 биквадов на канал), подъём одного канала ≤ +2 dB (остальное — срезом другого).
- Абсолютная коррекция комнаты (к ровной АЧХ) — **не делается** (микрофон телефона не откалиброван; профили динамиков уже дают абсолютную коррекцию).
- Результат хранится в записи пары (рядом с trim), применяется в цепочке устройства (§1.3), сбрасывается при сбросе калибровки.
Приёмка: после калибровки повторная запись — разность L/R ≤ ±1 dB (300 Гц–10 кГц, 1/3 окт.) в той же точке; в точке, смещённой на 0,5 м, разность не хуже, чем без коррекции.

### A6. Сцена

**A6.1 Перенос текущей ширины/глубины (Android spatial) в ядро** без изменения звука (null-тест против Kotlin ≤ −100 dB), после чего она работает и на iOS. Далее — только улучшения, подтверждённые метриками корпуса (стабильность центра, моно-совместимость ≤ 0,5 dB, предзвон ≤ −50 dB при окне 2048 — текущее значение −36…−40 dB, см. `docs/audio-algorithms.md` §7).

**A6.2 XTC для стереотелефона в Solo** (геометрия известна из профиля: разнос излучателей, их несимметрия).
- Модель тракта 2×2: свободное поле + модель тени головы (сферическая голова, модель Брауна–Дуды), слушатель на 0,45 м по оси.
- Синтез: регуляризованная инверсия по Тихонову с частотно-зависимым β, ограничивающим усиление фильтров ≤ +10 dB; полоса 500 Гц–8 кГц; ограничение «ровной ипсилатеральной АЧХ» (подавление перекрёстного пути без окрашивания прямого); КИХ 256 отводов на путь, разбиение на блоки (равномерная разбиваемая свёртка).
- Перед XTC обязательна коррекция обоих излучателей по A2 (несимметричные излучатели — разговорный и нижний).
- **Ворота (go/no-go):** лабораторный замер двумя UMIK в точках ушей (разнос 0,17 м) или макетом головы: подавление перекрёстного пути ≥ 12 dB в 1–6 кГц на оси и ≥ 6 dB при смещении слушателя ±5 см / ±10 см по расстоянию; окрашивание прямого пути ≤ ±1,5 dB. Не выполнено — блок остаётся только в режиме разработчика (как текущий XTC Android).

**A6.3 XTC для пары двух телефонов** — только решение «да/нет» по результатам A4 и A5: требуется акустическая синхронизация ≤ 10 мкс p95 и совпадение L/R ≤ ±1 dB. В программе A реализуется лишь при выполнении обоих условий; иначе фиксируется в документации как невыполнимое на текущих устройствах с измеренными числами.

## 4. Процесс исполнения (для Sonnet)

1. Определить рабочую линию: `git -C /Users/restart/Downloads/SoundField branch --show-current`; ветка этапа — `git switch -c claude/audio-a<N>-<кратко> <рабочая линия>`. `main` устарел — не использовать.

   - `sh tools/dsp_check.sh` (с A0) — тесты ядра + `sflab` без регрессий;
   - Android: `JAVA_HOME=/opt/homebrew/opt/openjdk@17 android/gradlew -p android --offline -q assembleDebug testDebugUnitTest` (предварительно `cp /Users/restart/Downloads/SoundField/android/local.properties android/`);

   - векторы протокола на обеих платформах (если менялся протокол).
5. Версии: следующие после текущих в рабочей линии (Android `versionName`/`versionCode`; iOS `MARKETING_VERSION`/`CURRENT_PROJECT_VERSION` в `ios/project.yml` и `pbxproj`; `SFDSP_VERSION`; `PROFILES_VERSION` при изменении профилей).
6. Документация в том же наборе изменений: `docs/audio-algorithms.md` (алгоритм, параметры, таблица «до/после»), README (раздел версии).

8. Что требует физического участия человека (сообщить пользователю заранее одним списком, не по ходу): покупка/подключение измерительного микрофона (A2.1), сеансы измерений на телефонах (A2, A4.6, A6.2), прослушивание отобранных вариантов виртуального баса (A3.3) в режиме разработчика.
