# ТЗ: офлайн-прототип ширины и глубины сцены (шаг 0)

Основание: `docs/width-depth-synthesis.md` §5–6. Исполнитель: Codex. Код приложения **не меняется** — это
инструмент на ПК (Mac) в `tools/spatial-proto/`. Версия инструмента — константа `PROTO_VERSION = "0.1.0"` в
`render.py`; поднимать при каждом изменении обработки (номер пишется в ключ теста, п. 6).

## 1. Зачем

Проверить вслепую, на реальной паре телефонов, дают ли выбранные методы слышимую ширину и глубину **без ухудшения
центра и тембра** — до того, как встраивать процессор в приложение. Попутно измерить реальную стабильность
синхронизации L/R пары и проверить XTC на одном телефоне со стереодинамиками.

Принцип: приложение уже раскладывает стереофайл по телефонам (L — Server, R — Point). Обработанный офлайн WAV,
добавленный в очередь, звучит так же, как звучал бы встроенный процессор на Server, — с реальными динамиками и
реальными ошибками синхронизации.

## 2. Условия (ограничения пользователя)

- **Измерительных и бинауральных микрофонов нет.** Объективные замеры — только запись телефоном в точке
  прослушивания (п. 7). Основной критерий — слух.
- **Музыкальный материал — только джаз** (файлы пользователя, FLAC/WAV). Плотный поп, оркестр и речь не
  проверяются — ограничение фиксируется в отчёте. Синтетические сигналы (п. 4.2) генерирует сам инструмент.
- Пара: Xiaomi 14 Ultra + Redmi 14C, расстояние 1,5–2 м, слушатель на равном расстоянии.

## 3. Структура

```
tools/spatial-proto/
  README.md            как запускать, как проводить тест, как читать отчёт
  requirements.txt     numpy, scipy, soundfile, pyloudnorm (без сетевых зависимостей)
  config.yaml          все параметры вариантов (п. 5) — не в коде
  render.py            рендер вариантов + кодирование (п. 6)
  signals.py           синтетические сигналы (п. 4.2)
  dsp/                 msband.py (W2), ambient.py (W3/D4/D3), reflections.py (W6), coherence.py, limiter.py, xtc.py
  analyze_files.py     объективные метрики по отрендеренным файлам (п. 7.1)
  analyze_recording.py метрики по записи телефоном (п. 7.2, 7.3)
  score.py             сводка оценок слушателей (п. 8)
  tests/               модульные тесты DSP (п. 10)
```

Вход: папка с исходными джазовыми треками. Выход: `out/<дата>/tracks/` (файлы для телефонов), `out/<дата>/key.json`
(ключ — не открывать слушателям), `out/<дата>/report_files.md`.

## 4. Материал

### 4.1 Музыка
- Пользователь кладёт 3–5 джазовых треков. Из каждого вырезается фрагмент 30–45 с (время начала — в `config.yaml`;
  по умолчанию автоматический выбор самого громкого 40-секундного участка по LUFS краткосрочному).
- Желательно разное: трио (контрабас по центру, мало инструментов), состав с духовыми, вокальный джаз (центральный
  голос — главный индикатор центра). Состав — в README как рекомендация пользователю.
- Ресемплинг в 48 кГц (как движок), стерео. Моно-исходники отклонять с сообщением.

### 4.2 Синтетические сигналы (генерирует `signals.py`)
| Код в ключе | Сигнал | Зачем |
|---|---|---|
| `pink_center` | розовый шум моно (L = R), 20 с | окраска и развал центра, гребёнка |
| `pink_stereo` | некоррелированный розовый шум L/R, 20 с | ширина «чистого» рассеянного поля |
| `clicks_center` | щелчки моно раз в 0,5 с | размазывание транзиентов, фокус центра |
| `sync_probe` | пары чирпов 1–6 кГц по 20 мс: чирп только в L, через **100 мс** чирп только в R; пары раз в 1 с, **10 мин** | замер синхронизации пары (п. 7.3). Без обработки, не участвует в слепом тесте |
| `channel_id` | «L»-тон 500 Гц только в L, затем «R»-тон 1 кГц только в R | проверка, какой динамик какой |

## 5. Варианты обработки

Все варианты — одна платформонезависимая функция `process(stereo, variant_params) -> stereo`, одинаковая задержка
обоих каналов, частота 48 кГц. Задержка обработки компенсируется (выход выровнен по времени с исходником).

| Код | Состав | Роль в тесте |
|---|---|---|
| `REF` | без обработки | скрытый эталон |
| `ANCHOR_MONO` | (L+R)/2 в оба канала | нижний якорь «узкая сцена» |
| `ANCHOR_OVER` | W1: M/S во всей полосе, side +8 дБ | якорь «переобработка» (фазовость, развал центра) |
| `W2_LO` | W2 умеренно | базовый слой |
| `W2_HI` | W2 сильнее | предел базового слоя |
| `W2_W3` | W2_LO + W3/D4 (+D3) | основной кандидат |
| `W2_W3_W6` | W2_W3 + W6 | проверка ранних отражений |

### 5.1 Управление по когерентности (`coherence.py`) — применяется в W2 и W3
- STFT 2048 / шаг 512, окно sqrt-Hann (анализ и синтез), 48 кГц.
- Межканальная когерентность по бинам со сглаживанием по времени (постоянная ~80 мс) и по частоте (~1/6 октавы).
- Вес расширения `w(k,t) = clamp((1 − coh − c0) / (1 − c0), 0, 1)`, `c0` в конфиге (по умолчанию 0,3).
- Защита транзиентов: детектор всплеска энергии (спектральный поток); на кадрах атаки вес × 0,3 с восстановлением
  за ~30 мс.
- Ниже `f_lo` (по умолчанию 300 Гц) вес = 0 — бас не трогаем никогда.

### 5.2 W2 — M/S по полосам (`msband.py`)
- M = (L+R)/2, S = (L−R)/2. Полосы: < 300 Гц — S без изменений; 300 Гц – 5 кГц — S × g_mid; > 5 кГц — S × g_hi.
  Переходы — фильтры Линквица–Райли 4-го порядка (суммарно плоские).
- Усиление S модулируется весом когерентности (5.1): в когерентных (центральных) областях → 1.
- `W2_LO`: g_mid = +3 дБ, g_hi = +2 дБ. `W2_HI`: +6 / +4 дБ.
- Энергия M не меняется. Общий уровень выравнивается на этапе п. 6.

### 5.3 W3/D4/D3 — прямой / рассеянный (`ambient.py`)
- Разложение по когерентной маске (5.1): рассеянная часть `A = X · (1 − coh_mask)`, прямая `D = X − A`
  (для каждого канала). Маски сглажены во времени (≥ 50 мс), чтобы не было «музыкального шума».
- Прямая часть — без изменений.
- Рассеянная часть выше 300 Гц:
  - декорреляция каналов: разные цепочки фазовых фильтров (allpass) для L и R, групповая задержка ≤ 5 мс;
  - D4: рассеянное чуть тише прямого на −1…−3 дБ (параметр) и расширено (S рассеянной части × g_amb, +3 дБ);
  - D3: мягкий спад ВЧ рассеянной части −2 дБ на 8 кГц (полочный фильтр).
- Реверберацию **не добавлять** — только перераспределение существующей энергии.

### 5.4 W6 — ранние боковые отражения (`reflections.py`)
- 3–4 отвода 7–25 мс, каждый в **противоположный** канал (L→R, R→L), уровень −18…−14 дБ относительно прямого,
  полоса 500 Гц – 6 кГц, разные задержки для L и R (без симметрии, чтобы не было гребёнки в моно).
- Подаётся только рассеянная часть (из 5.3), не прямая.

### 5.5 Выход
- Лимитер с заглядыванием вперёд 5 мс, потолок −1 dBTP (`limiter.py`); сколько раз сработал — в отчёт.

## 6. Слепое кодирование и выравнивание громкости

- Все варианты одного фрагмента выровнены по интегральной громкости (ITU-R BS.1770, `pyloudnorm`) к −18 LUFS,
  затем лимитер. Отклонение после лимитера ≤ 0,3 LU — иначе ошибка рендера. **Без этого тест недействителен**:
  громче = «лучше».
- Имя файла: `<фрагмент>-<3 случайные буквы>.wav`, например `J2-QKF.wav` (фрагмент — порядковый номер, вариант
  скрыт). 48 кГц, 24 бит, **без тегов** (приложение показывает название из тегов; без тегов — имя файла).
- `key.json`: `PROTO_VERSION`, дата, параметры `config.yaml`, соответствие код → вариант, LUFS, пики, срабатывания
  лимитера.
- Для каждого слушателя — свой порядок (`render.py --listener <имя>` печатает перемешанный порядок треков
  фрагмента; сами файлы одинаковые).

## 7. Объективные замеры

### 7.1 По файлам (`analyze_files.py`) — без телефонов
Для каждого варианта относительно `REF`:
- отклонение АЧХ **моно-суммы** (L+R) по 1/3-октавным полосам 100 Гц – 12 кГц — окраска центра и провал в моно;
- межканальная когерентность по полосам (ниже = шире);
- отклонение АЧХ `pink_center` после обработки — гребёнка и окраска центра;
- огибающая `clicks_center` — размазывание атаки (ширина пика, мс).
Отчёт `report_files.md`: таблица + графики PNG.

### 7.2 По записи в точке прослушивания (`analyze_recording.py`)
- Запись любым телефоном (диктофон, WAV/без обработки, если есть такая настройка), лежащим в точке слушателя
  микрофоном вверх. Если у телефона стереозапись — сохранить стерео.
- Воспроизводится плейлист «замер»: `pink_center` и `pink_stereo` во всех вариантах подряд с паузами 2 с
  (порядок из `key.json`), рендерит `render.py --measure`.
- Скрипт находит сегменты по паузам и считает: АЧХ каждого варианта относительно `REF` в точке слушателя
  (окраска с учётом реальных динамиков); если запись стерео — межмикрофонную когерентность как **грубый**
  показатель ширины (помечать в отчёте как ориентировочный).

### 7.3 Синхронизация пары (`analyze_recording.py --sync`)
- Запись 10-минутного `sync_probe` в точке слушателя.
- Для каждого чирпа — время прихода (взаимная корреляция с эталоном, уточнение до долей сэмпла параболой).
  Интервал L→R минус номинальные 100 мс = межканальная ошибка + постоянная геометрическая разница.
- Поправка на часы записывающего телефона: по ряду интервалов L→L (номинал 1 с) оценить отношение частот
  записи (ppm) и пересчитать интервалы L→R. Без поправки 20 ppm дали бы 2 мкс на 100 мс — в пределах допуска,
  но оценка ppm пишется в отчёт. Интервал 100 мс выбран, чтобы ход часов записи не маскировал ошибку
  синхронизации (на интервале 1 с те же 20 ppm дали бы 20 мкс).
- Отчёт: медиана (включает геометрию — не ошибка синхронизации), **разброс относительно медианы**: σ, p95, max,
  график во времени. Разброс не зависит от расстановки и является метрикой стабильности синхронизации.
- Цель из синтеза: p95 разброса ≤ 50 мкс. Результат — вход для ТЗ на дробную задержку.

## 8. Слуховой тест и сводка (`score.py`)

- Процедура — в README для пользователя, коротко: вся пара на 1,5–2 м, слушатель на равном расстоянии, голова
  неподвижна; громкость одинакова для всех треков; внутри фрагмента треки слушаются в порядке для этого слушателя,
  можно переключать сколько угодно.
- Шаблон `scores_<слушатель>.csv`: фрагмент, код, оценки 0–100 по атрибутам: **ширина, глубина, центр (фокус
  голоса/контрабаса), окраска (100 = нет), естественность, общее предпочтение**; свободный комментарий.
- Дополнительный повтор одного фрагмента со смещением головы на ±10 см влево/вправо — отдельная колонка «центр
  при смещении».
- `score.py` раскрывает коды по `key.json`: медиана и межквартильный размах по вариантам и атрибутам; отбрасывает
  слушателя, если он оценил `REF` ниже 70 по «естественности» больше чем в половине фрагментов (не узнал эталон).
- **Критерий провала варианта:** медиана «центр» или «окраска» ниже `REF` более чем на 10 пунктов, либо отклонение
  моно-суммы > 2 дБ в любой полосе 200 Гц – 5 кГц (7.1).
- **Критерий успеха:** медиана «ширина» или «глубина» выше `REF` на ≥ 15 пунктов при непровале.

## 9. Часть B — XTC на одном телефоне (Xiaomi 14 Ultra, соло)

Отдельная команда `render.py --xtc`, в слепой тест пары не входит.
- Геометрия: два динамика телефона в горизонтальном положении, расстояние между ними — параметр
  (по умолчанию 0,15 м, уточнить линейкой), слушатель по центру на 0,4 / 0,6 м (два набора).
- Модель: точечные источники + сферическая голова (упрощённая HRTF), XTC-фильтры с регуляризацией, рабочая полоса
  500 Гц – 6 кГц, вне полосы — без обработки. Параметр регуляризации — три значения (слабая/средняя/сильная).
- Материал: те же джазовые фрагменты + `pink_stereo` + `channel_id`.
- Выход: `out/<дата>/xtc/` с кодовыми именами и ключом, варианты: `REF`, XTC × 3 регуляризации × 2 расстояния.
- Воспроизведение: любой системный плеер на 14 Ultra (соло-режим SoundField ещё не готов); **системные эффекты
  (Dolby/«улучшение звука») выключить** — указать в README. Сначала `channel_id`, чтобы убедиться в ориентации.
- Оценка — те же атрибуты, слушатель неподвижен; отдельная пометка «звук вышел за пределы телефона: да/нет».

## 10. Проверки качества самого инструмента (`tests/`)
- `process(REF-параметры)` = вход (побитово после выравнивания задержки).
- W2 при g = 0 дБ: разница с входом < −90 дБ.
- Сумма полос Линквица–Райли плоская ±0,1 дБ.
- STFT-анализ/синтез без изменений: ошибка реконструкции < −80 дБ.
- Моно-вход (L = R) через W2/W3: выход тоже моно (разница L−R < −60 дБ) — когерентная защита работает.
- Выравнивание громкости: все варианты в ±0,3 LU.
- Детерминизм: одинаковый `seed` → одинаковые коды и файлы.

## 12. Приёмка
1. `render.py` на 3 джазовых файлах за один запуск создаёт треки, ключ и отчёт по файлам; тесты п. 10 проходят.
2. Треки добавляются в очередь SoundField и показываются под кодовыми именами (без названий исходника).
3. `analyze_recording.py --sync` на тестовой записи (сгенерировать искусственно: чирпы с известным джиттером 0/20/100 мкс
   и шумом) восстанавливает разброс с точностью ≤ 5 мкс.
4. `score.py` на заполненном вручную примере выдаёт таблицу и вердикты провал/успех.
5. `render.py --xtc` создаёт варианты и ключ.
