## 2. Продукт за одну страницу

SoundField — приложение, которое превращает два телефона в стереопару: один играет левый канал (L), другой правый (R). Один телефон тоже может играть сам (режим **Solo**). Телефоны связаны по одной сети Wi‑Fi; внешнего оборудования нет.

### Роли и термины

| Термин | Значение |
|---|---|
| **Server** | Телефон, который хранит и обрабатывает музыку и задаёт эталон времени. Играет свой канал и отправляет второй канал на Point |
| **Point** | Второй телефон. Получает по Wi‑Fi только свой канал (уже обработанный) и играет его в заданный момент |
| **Solo** | Один телефон играет сам, в стерео, без пары |
| **Общая шкала времени** | Server объявляет: «кадр F звучит в момент `anchor + (F − anchorFrame)/48000` по часам Server». Кадр — один отсчёт стерео (частота 48 кГц) |
| **Эпоха** | Номер версии шкалы. Любая команда play, pause, перемотка, смена канала создаёт новую эпоху с большим номером. Пакеты старых эпох Point отбрасывает |
| **Голова** (`readyFrames`) | Номер кадра, до которого звук источника уже принят и готов. Дальше головы читать нельзя |
| **Позиция** | Номер кадра, который играет в данный момент по шкале |
| **Запас** | Голова минус позиция: сколько звука накоплено впереди воспроизведения |
| **Сцена** | Необязательная обработка Server: ползунки «Ширина», «Глубина», «Высота» (расширение стереобазы, отражения помещения, окраска «выше горизонта»). Работает потоково через STFT (окно 2048 кадров, шаг 512). Все ползунки в нуле — обработка выключена |
| **Предлимитер** | Ограничитель пиков на Server перед разделением каналов, потолок −1,5 dBTP (true-peak). Локальный канал и сеть читают один и тот же сигнал |

### Связь и синхронизация

- **Управляющий контур (TCP).** Сопряжение, роли, состояние плеера, эпохи шкалы, команды, heartbeat.
- **Медиаконтур.** Server отправляет Point его канал по UDP пакетами по 384 кадра (8 мс), PCM 24 бит, моно (только канал Point), с номером кадра и плановым моментом воспроизведения. Point отправляет Server пакеты `PING` (для часов) и `NACK` (перезапрос потерянных). Параллельно по TCP Point заранее получает до 30 с своего канала; при сбое TCP используется UDP.
- **Часы.** Point оценивает смещение и дрейф своих часов относительно Server по минимальным задержкам в каждом направлении (корзины по 2 с, взвешенная регрессия за ~80 с). Поправка применяется не быстрее 2 мкс/с; скачок больше 2 мс считается сменой маршрута и применяется сразу.
- **Корректор воспроизведения.** Каждый телефон знает по `AudioTrack.getTimestamp()`, когда первый кадр блока выйдет из динамика. Корректор читает источник с дробной позиции 32-точечным sinc (256 фаз, окно Кайзера) и меняет скорость чтения в пределах ±200 ppm. Целые отсчёты не пропускаются и не повторяются. При ошибке больше 20 мс (960 кадров) выполняется жёсткий переход.
- **Jitter buffer Point.** Кольцо около 2,7 с, адресуемое абсолютным номером кадра. Пропуск в нумерации пакетов → `NACK` через 12 мс, до 4 повторов. Server перепосылает пакет, если его кадры ещё не проиграны.

### Константы времени (объект `SF`, `android/app/src/main/java/app/soundfield/core/Constants.kt`)

| Константа | Значение | Смысл |
|---|---|---|
| `SAMPLE_RATE` | 48 000 Гц | Единая частота дискретизации |
| `PACKET_FRAMES` | 384 | Кадров в одном UDP-пакете (8 мс) |
| `LEAD_NS` | 400 мс | Server отправляет аудио на 400 мс вперёд |
| `START_DELAY_NS` | 300 мс | play и перемотка стартуют через 300 мс после команды (время разослать данные) |
| `PAUSE_LEAD_NS` | 150 мс | Пауза наступает через 150 мс, одновременно на обоих телефонах |
| `HEARTBEAT_MS` | 1000 мс | Период heartbeat |
| `LINK_TIMEOUT_MS` | 8000 мс | Разрыв пары по отсутствию данных |
| `HARD_RESYNC_FRAMES` | 960 (20 мс) | Порог жёсткого перехода корректора |

### Тракт на Server

```
источник (раньше только файл) → сцена (STFT) → предлимитер (−1,5 dBTP)
   → разделение каналов → рендер своего канала (эквалайзер, финальный лимитер −1,0 dBTP, AudioTrack)
                       → канал Point: UDP на 400 мс вперёд (+ TCP-предзагрузка)
```

Сцена и предлимитер читают источник через общий интерфейс `AudioSource` и не читают дальше `readyFrames`. Это исходное свойство тракта: так работает подгрузка длинных файлов, пока они декодируются.

### Платформы

- Android: Kotlin, Jetpack Compose, minSdk 26, targetSdk 35; общее DSP-ядро на C++ (`sfdsp`).
- iOS (Swift): для этой функции только роль Point. Версия iOS при реализации не менялась; как Point она играет поток, но источников не выбирает.
- До версии 1.11.0 источником были только локальные файлы. Версия 1.11.0 добавила Spotify и YouTube.

## 3. Задача и ограничения

**Задача.** Получить звук Spotify и YouTube как PCM внутри тракта SoundField, чтобы к нему применялись сцена, предлимитер, эквалайзер и отправка на второй телефон, и чтобы оригинал не звучал параллельно.

**Ограничения (все одновременно):**

1. Обычный серийный телефон: без root, ADB, Shizuku, Magisk, разблокировки загрузчика, системной подписи.
2. Пользователь ничего не настраивает и не тестирует; режим разработчика недопустим.
3. Оригинал не должен звучать с того же телефона параллельно с обработанным звуком.
4. Звук проходит через общий тракт и синхронно уходит на второй телефон.
5. На этом этапе YouTube нужен для музыки. Видео с синхронной картинкой — следующий этап.
6. Источник выбирается и работает на Server (в паре) либо в Solo.

**Предыстория.** Раньше шло отдельное исследование «StereoSplit»: один телефон разводит L на Bluetooth-колонку и R на свой динамик, источник — штатное приложение. Его инварианты включали запрет root, ADB, Shizuku. Захват звука именно Spotify в нём подтверждён не был; аппаратная проверка раздельного вывода тоже не была завершена. Задача SoundField другая: развод по физическим выходам не нужен, нужен PCM в собственный тракт. Из прежнего исследования взяты запреты и сведение о том, что Spotify запрещает системный захват своего звука.

## 4. Рассмотренные варианты и выбор

### Spotify

| Вариант | Что даёт | Решение и причина |
|---|---|---|
| Системный захват (`AudioPlaybackCapture`) официального приложения | Звук приложения | Отвергнут: приложение запрещает захват, система отдаёт тишину. Без привилегий не обходится (сведение из прежнего исследования и документации Android; на устройстве в этой работе не проверялось) |
| Привилегированный захват (ADB или Shizuku, источник `REMOTE_SUBMIX`) | Звук в обход запрета | Отвергнут: противоречит запрету root/ADB/Shizuku и принципу «пользователь ничего не настраивает» |
| App Remote SDK | Только управление, звука нет | Отвергнут |
| Web Playback SDK во встроенном окне со съёмом звука | Звук из плеера страницы | Оставлен запасным. Поток защищён Widevine, прохождение звука через Web Audio в Android WebView не проверено. Качество ниже (AAC 256 кбит/с). Вмешательство в страницу тоже против условий сервиса |
| Приёмник Spotify Connect на librespot | PCM в тракт SoundField | **Выбран** |

Причины выбора librespot:

- пользователь остаётся в официальном приложении Spotify, оно работает как пульт;
- оригинала на телефоне нет, глушить нечего;
- звук поступает с опережением, как файл, поэтому нет расхождения часов;
- Vorbis 320 кбит/с;
- не зависит от того, открыто ли приложение Spotify на экране (работа с выключенным экраном не проверена).

Цена: librespot — неофициальная реализация протокола; она нарушает условия Spotify, не пройдёт проверку Google Play, может сломаться при обновлении Spotify, нужен Premium. **Риск принят владельцем проекта. Это данность, не предмет обсуждения.**

### YouTube

| Вариант | Достоинства | Недостатки | Решение |
|---|---|---|---|
| Системный захват официального приложения | Штатный API, без серых зон; заодно покрывает YouTube Music | Системный запрос на каждый сеанс; оригинал приходится глушить громкостью; задержка около 1 с; синхронизация с картинкой в этом механизме невозможна | **Выбран** для этапа «музыка» |
| Окно YouTube внутри SoundField со съёмом звука из плеера страницы | Оригинал глушится сам; системного запроса нет; картинку можно синхронизировать (например, вторым скрытым плеером, идущим с опережением) | Вмешательство в страницу, что противоречит условиям сервиса; фоновое воспроизведение без Premium ограничено самим сайтом | Отложен до этапа «видео» |

Следствие: видео потребует второго механизма, а не доработки системного захвата.

## 5. Реализованная архитектура

### 5.1 Общий тракт живого потока

**`LiveSource`** (`android/app/src/main/java/app/soundfield/core/LiveSource.kt`) — источник без длины и без перемотки:

- PCM 48 кГц стерео, float, дописывается в кольцо на 30 с по абсолютному номеру кадра;
- `readyFrames` — голова; публикуется после записи данных;
- запись синхронизирована (пишут приёмник Spotify или поток захвата и движок), чтение без блокировок;
- чтение вне диапазона [голова − ёмкость, голова) возвращает тишину;
- `totalFrames` условно 30 суток, `complete = false`.

Воспроизведение идёт позади головы на **запас**.

| Параметр запаса | Значение | Основание |
|---|---|---|
| Цель | 1 с | Выбрана с избытком над минимумом |
| Минимум | 0,6 с | Опережение отправки на Point 400 мс + упреждение сцены и предлимитера около 100 мс + пакет |
| Максимум (только YouTube) | 1,8 с | Выше этого запас сбрасывается перепривязкой |
| Запас для старта Spotify | 0,9 с | Старт после паузы, когда накоплено |
| «Устаревший» участок | 6 с | Если голова ушла от места паузы дальше, позиция считается от другого источника и берётся голова |

**Логика `liveTick`** — вызывается каждые 100 мс, пока выбран живой источник (псевдокод по `Engine.kt`):

```
liveTick():
  margin = head − position            # запас в кадрах
  if шкала играет:
    if YouTube и margin < −1 с:       # процесс стоял, позиция ушла за голову
        перепривязка: старт с головы (событие LIVE_REANCHOR)
    elif YouTube и margin < 0,6 с:    # источник молчит (пауза, подгрузка)
        append(тишина, до цели 1 с, не больше 2 с)   # шкалу не останавливаем (LIVE_PAD)
    elif margin < 0,6 с:              # Spotify
        остановить шкалу на текущем кадре (новая эпоха, не играет); LIVE_STARVED
    elif YouTube и margin > 1,8 с:
        перепривязка (LIVE_REANCHOR)
  elif источник хочет играть:
    startLiveIfReady()   # старт через 300 мс

startLiveIfReady():
  YouTube: старт с кадра (head + 300 мс − 1 с): к моменту старта голова уйдёт вперёд, запас станет целевым
  Spotify: старт с места паузы, если head − frame ≥ 0,9 с
```

Раз в 5 с пишется телеметрия `LIVE_STATE` (вход, играет ли, голова, запас, коррекция часов в ppm, пик последних 0,5 с в dBFS). Пик отличает «источник молчит» от «звук не доходит». Вставки тишины, перепривязки и остановки Spotify пишутся как `LIVE_PAD`, `LIVE_REANCHOR`, `LIVE_STARVED`.

**Отказ от TCP-предзагрузки для живого потока.** Обычный путь заранее передаёт Point до 30 с звука по TCP и ждёт буфер на Point до 2 с. Для живого потока впереди только запас, ждать нечем, поэтому предзагрузка отключена: Point получает звук по UDP с опережением 400 мс.

**Управление.** Кнопки ⏮ ▶ ⏭ и команды с Point в живых режимах уходят в источник: для Spotify командами Connect, для YouTube системными медиаклавишами. Перемотка, пропуск и выбор трека игнорируются. Потеря аудиофокуса (звонок) ставит на паузу источник, а не только шкалу: иначе источник тут же запустил бы воспроизведение снова. В Solo фоновый сервис не останавливается, пока выбран живой источник.

### 5.2 Spotify: приёмник Connect на librespot

Библиотека `libsfspotify.so` (Rust, librespot 0.8.0, JNI; `spotify/` и `android/app/src/main/java/app/soundfield/spotify/SpotifyReceiver.kt`). Размер собранной библиотеки arm64 — 7 921 976 байт (около 7,6 МБ). Собирается отдельным скриптом и не обязательна: без cargo или NDK приложение собирается без источника Spotify, кнопка сообщает об этом.

**Подключение без экрана входа.**

- Телефон объявляется в сети как устройство Spotify Connect «SoundField» (тип `Speaker`).
- Библиотека поднимает только HTTP-сервер zeroconf. Службу `_spotify-connect._tcp` (TXT: `CPath=/`, `VERSION=1.0`, `Stack=SP`) объявляет Kotlin через `NsdManager`: в librespot-discovery 0.8.0 подключаемый бэкенд mDNS сделать нельзя, поэтому в проекте лежит копия крейта с небольшим патчем (HTTP без собственного mDNS и доступ к номеру порта).
- Приложение Spotify передаёт учётные данные, когда пользователь выбирает устройство. Они кэшируются в каталоге приложения; при следующем запуске устройство подключается само, с повторами (задержка от 2 до 60 с).
- При работе держится multicast lock Wi‑Fi.

**Формат звука.** Vorbis 320 кбит/с → float 44,1 кГц стерео → `SampleRateConverter` ядра (полифазный sinc с окном Кайзера, подавление зеркал ≥ 120 dB, неравномерность ≤ ±0,01 dB до 20 кГц) → 48 кГц → `LiveSource`.

**Противодавление.** Декодер librespot идёт быстрее реального времени. Колбэк `onPcm` (поток librespot) после записи блока ждёт, пока впереди позиции больше 2,5 с звука, но не дольше 400 мс за вызов, шагами по 10 мс. Причина ограничения: на этом же потоке librespot исполняет паузу, перемотку и смену трека; долгая блокировка заморозила бы команды Connect.

```
onPcm(samples):
  live.append(resample(samples))
  waited = 0
  while не released и waited < 400 мс и (head − position) > 2,5 с:
      sleep 10 мс; waited += 10
```

**События и действия движка.**

| Событие | Действие движка |
|---|---|
| `SESSION_CONNECTED` | Название «Spotify», подсказка «Включите музыку в Spotify» |
| `PLAYING` | Источник хочет играть; если шкала стоит и запас набран, старт через 300 мс |
| `PAUSED` | Пауза общей командой, одновременно на обоих телефонах (через 150 мс) |
| `TRACK` | Название и исполнитель трека в плеер |
| `FLUSH` | Принятый, но не сыгранный звук устарел: шкала переносится на голову (новая эпоха) |
| `STOPPED`, `SESSION_DISCONNECTED` | Источник не хочет играть; в поток дописывается 1 с тишины, чтобы хвост не обрезался запасом |
| `ERROR` | Запись в телеметрию |

**Определение `FLUSH`** выполняется внутри приёмника по событиям плеера librespot перед записью следующего пакета: после перемотки, переключения трека пользователем, остановки, ухода устройства. При естественном (gapless) переходе к следующему треку `FLUSH` не посылается: перед переходом плеер присылает `EndOfTrack`, и следующая загрузка не считается сбросом. Хвост предыдущего трека доигрывается.

**Громкость.** Громкость в приложении Spotify программная, применяется до нашего тракта.

**Сборка.** TLS — rustls с ring: без OpenSSL и без cmake при кросс-сборке. `Cargo.lock` фиксирует `vergen` 9.0.6: версия 9.1.0 ломает сборку `librespot-core`. Зависимости librespot закреплены точной версией `=0.8.0`.

### 5.3 YouTube: системный захват

**Захват.** `CaptureService` (`android/app/src/main/java/app/soundfield/capture/CaptureService.kt`) — foreground-сервис типа `mediaProjection`. Читает `AudioRecord` с `AudioPlaybackCaptureConfiguration`:

- фильтр по UID приложений `com.google.android.youtube` и `com.google.android.apps.youtube.music`, если они установлены; иначе весь медиазвук других приложений (usage MEDIA, GAME, UNKNOWN, свой UID исключён);
- формат: 48 кГц стерео, сначала float, при отказе 16 бит; буфер не меньше 200 мс; чтение блоками по 10 мс в потоке с приоритетом аудио;
- нужны разрешение `RECORD_AUDIO` и системный запрос MediaProjection на каждый сеанс; приложение, запретившее захват (Spotify), отдаёт тишину;
- запрос на Android 14+ сделан сразу на весь экран (`MediaProjectionConfig.createConfigForDefaultDisplay`): по умолчанию диалог предлагает «одно приложение» с выбором из списка, а нужны одно нажатие и предсказуемый результат. Звук всё равно фильтруется по UID.

**Глушение оригинала** (`Engine.enterCaptureAudio`):

1. Громкости медиа и будильника сохраняются в настройках (возвращаются при выходе и при следующем запуске после аварийного завершения).
2. Громкость медиа ставится в 0; громкость будильника — в ту же долю шкалы, что была у медиа.
3. Вывод Server пересоздаётся с `USAGE_ALARM`. Поток громкости метрик «выход заглушён» определяется по реально используемому потоку.
4. Аудиофокус не берётся: иначе YouTube встал бы на паузу.
5. Кнопка «громче» вне SoundField поднимает медиапоток; приёмник `android.media.VOLUME_CHANGED_ACTION` переносит шаги на поток будильника и возвращает медиа в 0. Кнопка «тише» вне SoundField система не сообщает (медиа уже в нуле): убавлять можно только в SoundField.
6. Поток специальных возможностей (`STREAM_ACCESSIBILITY`) не взят: по устройству Android без активной службы доступности его громкость привязана к медиа (на телефоне не проверялось).
7. Маршрут «будильник → динамик» на одном из прежних телефонов (Xiaomi 14 Ultra) фиксировался в журналах прежнего исследования; слышимый вывод там доказан не был.

**Привязка часов (`LiveClockServo`).** Захват идёт по часам аудиотракта источника, шкала — по системным часам. Без коррекции расхождение в десятки ppm за час съедает запас. Сервопривод передискретизирует входной поток 32-точечным sinc ядра рендера:

```
каждые блок записи (~10 мс):
  error_s   = (margin − 48000) / 48000                     # margin в кадрах; ошибка запаса в секундах
  smoothed += (error_s − smoothed) · min(1, блок / (48000·1 с))   # сглаживание 1 с
  ratio_ppm = clamp(5000 · smoothed, −1000, +1000)          # k = 5000 ppm на секунду ошибки
  шаг чтения входа = 1 + ratio_ppm·1e-6
  выход = sinc-интерполяция входа по дробной позиции; append в LiveSource
пока воспроизведение не идёт (margin = null): сброс сглаживания, ratio = 0
```

Знак: запас больше цели — читаем вход быстрее (выход короче), запас меньше — медленнее. При отношении ровно 1 выход повторяет вход бит-в-бит с задержкой 15 кадров интерполятора. Постоянная времени замкнутого контура около 200 с: на ошибку 100 мс приходится 500 ppm.

| Измерение (JVM, `LiveSourceTest`) | Результат |
|---|---|
| Запас на цели | выход равен входу бит-в-бит |
| Уход часов источника 200 ppm, 15 минут | коррекция 197,8 ppm, ошибка запаса 39,6 мс (без привязки 180 мс) |
| Тон 10 кГц при предельной коррекции +1000 ppm | уровень +0,0002 dB |

**Разрывы потока.** Поток захвата не непрерывен: когда источник не играет (пауза, подгрузка), чтение просто встаёт, звук не поступает. Первая версия останавливала шкалу при исчерпании запаса и перезапускала её. Заменено дописыванием тишины до целевого запаса без остановки шкалы (`LIVE_PAD`). Если позиция ушла за голову больше чем на 1 с (процесс стоял), выполняется перепривязка к голове (`LIVE_REANCHOR`). Состояние «источник играет» берётся из `AudioManager.isMusicActive`.

**Задержка.** Звук отстаёт от действия в YouTube примерно на 1 с (целевой запас) плюс задержка захвата. Синхронизация с картинкой не делается.

### 5.4 Интерфейс

- Под кнопками плеера вместо заголовка «Очередь · n» стоит переключатель из трёх значков: Плеер (собственный), Spotify, YouTube. Знаки Spotify и YouTube нарисованы векторно.
- При выборе Spotify или YouTube скрываются значки работы с плейлистами и список треков. Они возвращаются при выборе «Плеер». Повторное нажатие на «Плеер» сворачивает и разворачивает список (по умолчанию развёрнут).
- Шкала времени и перемотка в живых режимах скрыты; место на экране сохранено.
- Источник переключается только на Server (в паре и в Solo). Point показывает выбранный: системный запрос захвата и приёмник Spotify живут на телефоне с музыкой.
- Название трека для Spotify приходит от librespot; для YouTube метаданных трека нет.
- На проводе в сообщение `state` добавлено поле `input` (`player` / `spotify` / `youtube`); протокол версии 3.

### 5.5 Схема потоков данных

```
 Spotify (приложение-пульт) ──Connect/zeroconf──► librespot (Rust, поток декодера)
      Vorbis 320 → PCM 44,1 кГц → SampleRateConverter → 48 кГц
                                                   │  противодавление: пауза записи, если впереди > 2,5 с
                                                   ▼
 YouTube / YouTube Music ──► AudioRecord (AudioPlaybackCapture, фильтр по UID)
      PCM 48 кГц ──► LiveClockServo (sinc, ±1000 ppm) ──┐
                                                   ▼    ▼
                                  LiveSource: кольцо 30 с, голова readyFrames
                                                   │
                       liveTick (100 мс): старт / тишина / стоп / перепривязка по запасу
                                                   ▼
                        сцена (STFT, ширина/глубина/высота) ──► предлимитер −1,5 dBTP
                                                   │
                      ┌────────────────────────────┴─────────────────────────┐
                      ▼                                                      ▼
   рендер своего канала Server (эквалайзер,                      канал Point: UDP на 400 мс вперёд
   финальный лимитер −1,0 dBTP, AudioTrack;                      (384 кадра, PCM 24 бит); TCP-предзагрузка
   YouTube: USAGE_ALARM, медиа = 0)                              для живого потока отключена
                                                                          ▼
                                                    Point: jitter buffer → корректор (sinc, ±200 ppm) → динамик
```

## 6. Что проверено и что нет

Статусы: **эмулятор** — проверено на эмуляторе Android 16 (arm64) в режиме Solo; **тесты** — проверено автоматическими тестами на JVM; **не проверено** — не запускалось.

| Проверка | Статус | Результат |
|---|---|---|
| Загрузка `libsfspotify.so`, запуск приёмника | эмулятор | Устройство объявлено (`SoundField._spotify-connect._tcp`), `GET /?action=getInfo` отвечает `status 101`, `deviceType Speaker` |
| Переключатель источников | эмулятор | Значки плейлистов, список и шкала времени скрываются; возврат на «Плеер» их возвращает |
| Запуск захвата | эмулятор | Сервис `mediaProjection` активен, вывод пересоздан с `USAGE_ALARM`, медиа 5 → 0, будильник 6 → 2 |
| Звук YouTube при нулевой громкости медиа | эмулятор | Доходит до `LiveSource`: пик −3…−8 dBFS |
| Возврат на «Плеер», перезапуск после принудительного завершения в режиме захвата | эмулятор | Громкости 5 / 6 восстановлены, вывод `USAGE_MEDIA` |
| Кольцо `LiveSource`, привязка часов `LiveClockServo` | тесты | См. таблицу в 5.3; всего в проекте 180 тестов, без падений |
| Логика движка `liveTick` и обработка событий Spotify | эмулятор (YouTube); для Spotify не проверено | Для захвата YouTube работа механизмов видна в эмуляторе (см. выше). Ветка Spotify (старт, остановка по запасу, `FLUSH`) не запускалась с реальным потоком |

Эмулятор был перегружен: процесс приложения замирал на 4–14 с. Поэтому устойчивость запаса и работа привязки часов в реальном времени на эмуляторе не оценивались; они проверены только тестами. Выводов о стабильности во времени по эмулятору не делалось.

**Не проверено вообще:**

- вход в Spotify и воспроизведение (аккаунта Spotify при проверке не было);
- обнаружение устройства приложением Spotify на том же телефоне;
- обнаружение устройства при нескольких сетевых интерфейсах и при изоляции клиентов в Wi‑Fi;
- любое поведение на реальных телефонах, включая Xiaomi;
- работа с выключенным экраном;
- маршрут `USAGE_ALARM` в паре и слышимый вывод через него;
- работа iOS в роли Point с живым потоком;
- прослушивание на слух (качество, задержка, артефакты привязки часов);
- работа в паре двух телефонов: проверки шли только в Solo.

## 7. Известные слабые места и открытые вопросы

1. **Кнопка «тише» вне приложения в режиме YouTube.** Система не сообщает о ней, потому что громкость медиа уже равна 0.
2. **Задержка YouTube.** Около 1 с плюс задержка захвата. Часть задержки заложена запасом 1 с против разрывов.
3. **Системный запрос на каждый сеанс захвата.** Один диалог, но каждый раз.
4. **Зависимость от неофициального протокола Spotify.** Обновление Spotify может сломать приёмник. Запасной путь (веб-плеер) не реализован и не проверен.
5. **Видео без синхронной картинки.** Звук отстаёт от картинки. Пока режим предназначен для музыки.
6. **Поведение производителей не известно.** Особенно Xiaomi (HyperOS): ограничения фоновых сервисов, маршрут потока будильника, обработка `VOLUME_CHANGED_ACTION`, обработка MediaProjection.
7. **iPhone как Point с живым потоком не проверен.** iOS не менялся.
8. **Позиция в приложении Spotify опережает слышимый звук** на величину буфера (ориентировочно до 2,5 с вперёд позиции плюс запас; это оценка по параметрам противодавления, не измерение).
9. **Пауза в Spotify и в паре (оценка, не измерение).** Пауза идёт общей командой через 150 мс, но задержка между действием пользователя в Spotify и паузой на телефонах не измерялась.
10. **Ограниченная блокировка в `onPcm`.** 400 мс за вызов — компромисс; если телефон и сеть не успевают, запас Spotify может опускаться ниже 0,6 с с остановкой шкалы (`LIVE_STARVED`). Частота таких остановок на реальных устройствах не известна (оценка риска, не измерение).
11. **Перепривязка YouTube** (`LIVE_REANCHOR`) даёт слышимый скачок; как часто она случается при реальной нагрузке, не известно.
12. **Метаданные YouTube** недоступны: название и исполнитель в плеере не показываются.

## 9. Вопросы

Владелец проекта ждёт прежде всего сильных идей, а не аудита ради аудита.

**A. Что сломается на реальных телефонах.** Что в этой архитектуре с наибольшей вероятностью откажет на реальных телефонах разных производителей и версий Android 10–16? Как предотвратить отказ или обнаружить его заранее, без участия пользователя? Нужны конкретные механизмы отказа (какой API, какая версия, какой производитель, какое наблюдаемое проявление), а не общие предостережения. Особо: `AudioPlaybackCapture` и MediaProjection на Android 10–16 (фильтр по UID, `USAGE_ALARM`, foreground-сервис, ограничения по версиям), `VOLUME_CHANGED_ACTION`, мультикаст и `NsdManager`, энергосбережение фоновых сервисов и Wi‑Fi, привязка потока будильника к громкости, маршрутизация вывода.

**B. Идеи, дающие качественный скачок.**

1. Существенно меньшая задержка YouTube при захвате (сейчас около 1 с плюс задержка захвата).
2. Видео YouTube с синхронной картинкой на паре телефонов.
3. Управление громкостью без ограничения «тише».
4. Избавление от системного запроса MediaProjection на каждый сеанс.
5. Получение метаданных трека YouTube (название, исполнитель).
6. Единый механизм для других сервисов: Apple Music, Tidal, YouTube Music, SoundCloud.

**C. Альтернативы, которые не рассмотрены.** Для каждого из двух входов (Spotify и YouTube) предложи варианты, которых нет в таблицах раздела 4, и объясни, чем они лучше выбранных. Перед тем как предлагать, проверь, не противоречит ли вариант запретам из раздела 3.

**D. Привязка часов и буферизация.** Есть ли более точная или более простая схема для потока реального времени с чужими часами и разрывами, чем: запас как регулируемая переменная, пропорциональный сервопривод 5000 ppm/с с пределом ±1000 ppm, сглаживание 1 с, тишина при разрывах и перепривязка при выходе запаса за 0,6–1,8 с? Рассмотри: оценку дрейфа вместо реакции на запас, адаптивный размер запаса по измеренной нестабильности, обнаружение разрывов по метке времени `AudioRecord.getTimestamp`, замену вставок тишины на растяжение сигнала, общую модель для Spotify и YouTube.

**E. Запасной путь для Spotify.** Что делать, если librespot перестанет работать (смена протокола, блокировка клиента, изменение условий)? Нужны варианты, которые укладываются в раздел 3 и не требуют от пользователя больше одного нажатия. Для каждого укажи, как заранее обнаружить отказ основного пути и как переключиться без вмешательства.

**Не нужно:** юридической оценки; пересказа этого документа; решений с root, ADB, Shizuku, внешними компьютерами и дополнительным оборудованием; решений, требующих от пользователя действий сверх одного нажатия.

## 10. Формат ответа

Структура ответа жёсткая, чтобы ответы разных моделей можно было свести в одну таблицу.

Заголовки разделов: `## A`, `## B`, `## C`, `## D`, `## E`. В каждом разделе — нумерованные пункты. Каждый пункт содержит поля в таком порядке:

```
N. <короткое название>
- Суть: 1–3 предложения.
- Что даёт: выигрыш (задержка, надёжность, синхронность, простота).
- Риск: что может пойти не так.
- Цена проверки: низкая / средняя / высокая.
- Как проверить без написания кода или минимальным экспериментом: конкретные шаги.
- Уверенность: высокая / средняя / низкая.
- Основание: документация Android/AOSP с названием API / собственный опыт / предположение.
```

После раздела E:

- `## Три пункта, с которых начал бы ты` — три пункта из A–E по порядку и одна фраза на каждый.
- `## Чего в документе не хватает для точного ответа` — список недостающих сведений.

Правила:

- Предположения помечай словом «предположение» и не выдавай за проверенные факты.
- Если ссылаешься на API Android, называй класс и метод; если помнишь версию, в которой поведение изменилось, указывай номер API.
- Не повторяй описание из этого документа.
- Пункт без способа проверки не принимается.
- Объём: сколько нужно, без вступлений и пересказа.
