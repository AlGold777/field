## 0. Решение и как мы страхуемся

Пользователь решил реализовать алгоритмы сразу в телефоне, без офлайн-слушания. Риск: настраивать звук на
устройстве, не зная заранее, есть ли слышимый выигрыш. Страховка встроена в само ТЗ:

1. **Всё выключаемо и выключено по умолчанию.** Главный переключатель «Пространство» — выкл. при установке.
   Каждый слой отключается отдельно.
2. **Слепое сравнение в скрытом режиме разработчика** (п. 9.3) заменяет офлайн-тест — для нас, не для пользователя.
3. **Инварианты проверяются тестами** (п. 12) — те, что пропустили 13 тестов прототипа (моно, центр, атаки,
   фазовость).
4. **Цифры по реальному коду — на Mac, не в телефоне**: пакет `dsp` без Android запускается задачей Gradle на любом
   WAV (п. 12.5); результат можно подать в `evaluate_algorithms.py`. В приложении выгрузки нет.
5. **Поэтапная сдача** (п. 14): каждый этап — отдельная версия-сборка, коммит и тег. Звук меняется только на этапах,
   где это ожидаемо.

### 0.2 Принцип: пользователь только наслаждается
Пользователь не тестирует, не измеряет, не подтверждает, не выгружает и не настраивает геометрию. Всё определяется
автоматически (таблица устройств, API, датчики); при неизвестности — тихо выбирается безопасный вариант.
Неподходящее устройству — скрыто, без объяснений (владелец старого телефона и так знает, что стерео у него нет, —
ему интересно быть частью пары). Все проверки, замеры и A/B — только в скрытом режиме разработчика (п. 9.3)
и в телеметрии.

## 2. Зависимости и порядок

- Пара (ширина/глубина/отражения, этапы S1–S5) — от соло не зависит, работает на нынешнем моно-выводе телефонов:
  каждый телефон играет свой канал `L′` или `R′`.
- **XTC (этап S7) требует соло-режима и стерео-вывода** из `docs/tz-solo-player.md` этап 1 (1.6.0). Если к началу
  S7 соло не готов — S7 откладывается, остальное сдаётся.
- Используется ограничитель пиков эквалайзера (`EqualizerProcessor.processLimiter`, 1.8.0) — второй не писать.
- Режим **Amplifier** (1.7.0, если будет готов): оба телефона играют L+R, межканальной сцены нет →
  `SpatialSource` в режиме обхода.
- **Немузыкальные источники не обрабатываются:** калибровка, метроном, проверка каналов, измерение уровня — всегда без
  пространственной обработки (сигналы калибровки должны оставаться точными). Обработка применяется только к
  `SourceMode.MUSIC`.

## 3. Архитектура

### 3.1 Цепочки
```
ПАРА, Server:
  декодер (стерео 48 кГц) → SpatialSource [STFT: маска → ширина(Side) → глубина(Mid) → ISTFT → отражения(Side)
                                            → связанный стерео-ограничитель → компенсация громкости]
    ├─ канал Server → рендер: корректор долями сэмпла → эквалайзер → громкость/баланс → ограничитель → выход
    └─ канал Point  → UDP/TCP (как сейчас, уже обработанный)
ПАРА, Point (без изменений логики):
  приём → корректор долями сэмпла → эквалайзер → громкость → ограничитель → выход
СОЛО, телефон со стереодинамиками:
  декодер → SpatialSource [... → XTC] → стерео-рендер → эквалайзер → громкость → ограничитель → выход
```

### 3.2 Платформонезависимое ядро
- Весь DSP — пакет `app.soundfield.dsp`: чистый Kotlin, **без импортов Android**, без выделения памяти в
  рабочем цикле. Тесты — JVM-модульные (`src/test`). Цель — переносимость на другие устройства
  (`project_audio_quality_direction`: телефоны — временная платформа).
- `app.soundfield.core`/`engine` — только интеграция: потоки, кэш, протокол, UI.
- БПФ: одна реализация на весь проект (реальное БПФ radix-2/split-radix на `DoubleArray`, либо JTransforms —
  выбрать одно; анализатор эквалайзера `EqSpectrumCapture` перевести на неё же).

## 4. Этап A — коррекция долями сэмпла (`PlayoutCorrector`)

Сейчас: целые кадры, при ошибке > 6 кадров (125 мкс) — пропуск или повтор одного сэмпла посреди буфера. Центр
«гуляет» в пределах ±125 мкс, а пропуск сэмпла — микроразрыв сигнала.

### 4.1 Новый алгоритм
- Позиция чтения — `Double` (кадр + доля).
- Скорость чтения на каждый колбэк `ρ = 1 + clamp(Kp·e + Ki·Σe, ±200 ppm)`, где `e` — сглаженная ошибка
  «идеальная позиция − фактическая» (как сейчас, фильтр 0,1). Порог 6 кадров убрать. `Kp`, `Ki` подобрать так, чтобы
  ошибка 100 мкс устранялась за ~5–10 с (постоянная времени петли ~3 с, п. 4.3) без перерегулирования > 10 %; значения — константы с комментарием.
- Жёсткий прыжок при |e| > 20 мс — как сейчас.
- Отсчёт на дробной позиции — **интерполяция оконным sinc**: 32 отвода, 256 фаз (многофазная таблица), окно
  Кайзера β ≈ 8,6. АЧХ ±0,1 дБ до 18 кГц, подавление зеркал ≥ 80 дБ. **Сначала проверить `core/Resampler.kt`** — если
  там уже многофазный sinc нужного качества, переиспользовать (правило AGENTS.md). Иначе — новая реализация в `dsp/`,
  и `Resampler` перевести на неё.
- Постоянная задержка интерполятора (16 кадров) одинакова на обоих телефонах и учитывается в `frameAt`, чтобы не
  сдвинуть сохранённую калибровку `trimMs`.
- `trimNs` применяется с полной точностью (дробная часть кадра больше не округляется): калибровка задержки
  впервые получает разрешение лучше 21 мкс.
- Интерфейс для рендеров: `corrector.position(i)` возвращает `Double`; рендер берёт кадры `floor(p)−15 … floor(p)+16`
  из источника (`source.sample` / `rx.read` / `tcpAudio.read`). Отсутствующие кадры (NaN) — как сейчас, недобор.

### 4.2 Метрики
`syncErrorUs` вместо `syncErrorMs` в `Diag`; в телеметрии — гистограмма |e| за окно (p50, p95, max) и число
жёстких прыжков. Индикатор L/R на плеере показывает мкс, когда < 1 мс.

### 4.3 Модель часов `ClockSync` — непрерывность (R1)
Сейчас модель `offset + drift` пересчитывается при каждой новой корзине замеров (`recompute()`), и её значение
для текущего момента может **скачком** сдвинуться на единицы–десятки мкс; пока регрессии нет (первые 12 с) — берётся
смещение лучшей корзины, скачки ещё больше. Старый корректор с порогом 125 мкс эти скачки не замечал; новый будет
точно им следовать, и центр сцены будет «вздрагивать».
- При каждом пересчёте логировать скачок: `Δ = новая_модель(now) − старая_модель(now)` → телеметрия `CLOCK_MODEL_STEP`
  (гистограмма |Δ| p50/p95/max за окно).
- **Плавный переход модели**: новая модель не подставляется сразу; разница `Δ` отрабатывается с ограничением
  скорости **≤ 2 мкс/с** (сверх наклона дрейфа). Исключения — первые 12 с после подключения и |Δ| > 2 мс (явная смена
  маршрута/сети): тогда сразу.
- Корректор (п. 4.1) не должен отслеживать шум модели: полоса петли ≈ 0,05 Гц (постоянная времени ~3 с) для малых
  ошибок; быстрое сближение — только при |e| > 1 мс.
- Честная метрика — только акустическая (п. 5). `syncErrorUs` показывает расхождение с **моделью**, а не с истиной;
  на экране подписать «по оценке часов».

### 4.4 Переключатель для сравнения и отката (R11)
Режим разработчика (п. 9.3): «Старый корректор (целые сэмплы)». По умолчанию выкл. Нужен для замера п. 5
«до/после» на одной паре и как быстрый откат, если на каком-то телефоне появятся проблемы. Удалить через одну
версию после приёмки.

### 4.5 Приёмка этапа A
- Модульный тест: синус 1 кГц, ошибка часов 100 ppm → остаточная ошибка позиции ≤ 2 мкс в установившемся режиме,
  искажения (THD+N) ≤ −90 дБ.
- Пара: p95 `syncErrorUs` за 30 мин ≤ 20 мкс (по оценке часов — внутренняя метрика).
- **Главный критерий — акустический**: «Замер синхронизации» (п. 5) с новым корректором и сглаженной моделью
  против старого корректора (п. 4.4) на той же паре и расстановке: p95 разброса не хуже и, цель, ≤ 50 мкс.
  `CLOCK_MODEL_STEP` p95 ≤ 10 мкс. Если акустический p95 > 50 мкс при хорошей внутренней метрике — ошибка в оценке
  часов по Wi-Fi; это вход для отдельного ТЗ на `ClockSync` (например, аппаратные метки времени, фильтр Калмана).

## 5. Этап B — замер синхронизации в приложении

Перенос `sync_probe` из прототипа в Diagnostics.
- Кнопка «Замер синхронизации (2 мин)» — **только в режиме разработчика** (п. 9.3), только в паре, Server. Server проигрывает пробу: чирп 1–6 кГц 20 мс только в L,
  через 100 мс — только в R, пары раз в секунду. Параллельно записывает **свой** микрофон (`MicRecorder`, как в
  калибровке).
- Обе записи и воспроизведение — на одном устройстве, поэтому поправка ppm не нужна, но её оценка (по L→L)
  остаётся как проверка.
- Анализ на телефоне: взаимная корреляция с эталоном, уточнение параболой, интервал L→R минус 100 мс. Медиана =
  геометрия + постоянные задержки (не ошибка). **Разброс относительно медианы (σ, p95, max) — метрика стабильности.**
- Во время замера: эквалайзер и пространственная обработка в обходе на обоих телефонах (проба — немузыкальный
  источник, п. 2); громкость фиксируется на 60 %, чтобы ближний динамик не перегружал микрофон Server. Проверка
  клиппинга записи (пик > −1 dBFS) → замер недействителен, подсказка «уменьшите громкость».
- Результат на экране + в телеметрии (`SYNC_PROBE_RESULT`). Цель для пространственной обработки: p95 ≤ 50 мкс.
- Портировать алгоритм из `tools/spatial-proto/analyze_recording.py`; модульный тест на синтетической записи из
  `tests/simulate_sync_recording.py` (сохранить 3 файла в `src/test/resources`): σ восстанавливается с ошибкой ≤ 5 мкс.

## 6. Этап C — потоковый процессор `SpatialSource`

### 6.1 Контракт
- `class SpatialSource(inner: AudioSource, …) : AudioSource`. Для всех потребителей (рендер Server, UDP-отправка,
  TCP-отправка, повторная отправка по NACK, `measurePointChannelSignal`) это обычный источник: `sample(frame, ch)`.
  Существующие места вызова не меняются — меняется только то, что кладётся в `ServerPlayState.source`.
- **Выход выровнен по времени со входом**: `out(frame)` соответствует `in(frame)`. Внутренняя задержка обработки
  (`L = n_fft + lookahead`) скрыта тем, что процессор идёт впереди.
- `readyFrames = min(inner.readyFrames, processedHead)` — тот же контракт, что у `SegmentedPcmSource`: отправители
  уже умеют ждать `readyFrames`, рендер уже считает недобор (`sourceMissingFrames`). Новых механизмов ожидания не
  делать.

### 6.2 Обработка вперёд и кэш
- Поток `sf-spatial` (приоритет выше фонового, ниже аудио) обрабатывает блоками по `hop` последовательно и пишет
  результат в кольцевой кэш стерео-кадров `FloatArray`.
- Объём кэша покрывает самое дальнее опережение потребителя: TCP-отправка держит до 30 с вперёд
  (`TCP_AUDIO_TARGET_FRAMES`) → кэш **40 с** (48 000 × 2 × 4 Б × 40 ≈ 15 МБ). Позади позиции воспроизведения держать
  2 с (для NACK и корректора).
- Скорость: процессор должен быть ≥ **20× реального времени** на Redmi 14C (п. 13), чтобы после перемотки первые
  кадры появлялись быстро.
- Без выделений памяти в цикле; все буферы — при создании.

### 6.3 Перемотка, новая эпоха, смена трека
- Если запрошенный кадр вне кэша (перемотка, новый трек) — перезапуск процессора с кадра `F − warmup`,
  `warmup = 1,0 с`: состояния сглаживания (когерентность, пики энергии, громкость) сходятся, выход разогрева
  отбрасывается. Для начала трека (`F < warmup`) — разогрев на первой секунде без вывода, затем обработка с начала.
- Время от перезапуска до готовности 200 мс после `F` должно быть ≤ 100 мс на Redmi 14C (1,2 с звука ×
  20× = 60 мс).
- Детерминизм: одинаковые вход и параметры → побитово одинаковый выход при любом размере блока потребителя.
  После разогрева выход совпадает с непрерывной обработкой с точностью ≤ −60 дБ (тест п. 12.3).

### 6.4 Смена параметров и A/B — одинаково на обоих телефонах
Проблема: процессор и кэш впереди воспроизведения до 40 с, а по TCP Point уже получил до 30 с старого звука.
Решение — «переобработка с кадра F»:
- При изменении параметров (или переключении A/B) Engine выбирает `F = кадр(сейчас + LEAD_NS + 200 мс)`.
- Процессор перезапускается с `F − warmup` с новыми параметрами (п. 6.3); на участке `F … F+50 мс` — перекрёстное
  затухание старого выхода (из кэша) в новый. Кадры до `F` не трогаются.
- **UDP**: отправка идёт на `LEAD_NS` вперёд — кадры ≥ F ещё не отправлены, ничего делать не нужно.
- **TCP**: отправитель перематывает курсор на `F` и отправляет заново. `TcpAudioBuffer.Slot.write` уже **перезаписывает**
  кадр с тем же номером в той же эпохе (массив меток `tags`) — доработка не нужна, но нужен модульный тест на это.
  Эпоха не меняется (иначе Point сбросит буфер и замолчит).
- Порядок гарантирует успеть: TCP-отправка идёт до 4× быстрее реального времени, а воспроизведение дойдёт до `F`
  только через ~0,6 с. Если к моменту `воспроизведение(F) − 100 мс` Point не подтвердил приём кадров от `F` (по
  существующему учёту `tcpAudioFramesSent`/буфера) — переход на новые параметры отменяется для этого `F` и
  назначается следующий `F` (телеметрия `SPATIAL_REPROCESS` с `result=deferred`).
- Итог: изменение слышно на обоих телефонах через ~0,6 с, одновременно, без разрыва. Для слайдеров — применять по
  отпусканию (`finished`) и не чаще раза в 300 мс во время перетаскивания.

### 6.5 Где включается
- `ServerPlayState.source` = `SpatialSource(musicSource)` только при `mode == MUSIC`, главном переключателе вкл.,
  режиме пары Stereo или соло с подходящим профилем (п. 8). Иначе — исходный источник (обход без копий).
- Переключение вкл/выкл — как смена параметров (п. 6.4), с перекрёстным затуханием, без новой эпохи.

### 6.6 Постепенное декодирование (R3)
Источник музыки — `SegmentedPcmSource`: декодер дописывает кадры, `readyFrames` растёт, `complete` — конец.
- Процессор не обрабатывает дальше `inner.readyFrames − L` (L — задержка процессора): иначе в кэш попадут нули вместо
  ещё не декодированных кадров, и их уже никто не пересчитает.
- Хвост трека: после `complete` — дообработка последних `L` кадров с нулевым дополнением.
- `readyFrames` процессора всегда ≤ `inner.readyFrames`; недобор при медленном декодере учитывается существующим
  механизмом (`sourceMissingFrames`), как сейчас.

### 6.7 Смена трека (R7)
- Обёртка `SpatialSource` — только для текущего трека и (заранее) для следующего; кэш 15 МБ на экземпляр,
  не больше двух экземпляров, память — из общего пула (без повторных выделений при каждом треке).
- За 3 с до конца текущего трека, если следующий трек уже декодируется (`selectTrack` предзагрузка), создаётся его
  `SpatialSource` и выполняет разогрев — к моменту перехода первые кадры готовы.

## 7. DSP (этапы D–G) — точная спецификация

Общие параметры: 48 кГц; STFT `n_fft = 2048`, `hop = 512`, окно sqrt-Hann для анализа и синтеза (идеальное
восстановление при 75 % перекрытии проверить тестом; при необходимости нормировать). Для каждого кадра `t` и бина `k`:
`M = (L+R)/2`, `S = (L−R)/2`. Все параметры — в профиле (п. 8), не в коде.

### 7.1 Анализ (общий для слоёв)
- Мощности `P_L, P_R, P_M, P_S`, взаимный спектр `X = L·conj(R)` — экспоненциальное сглаживание по времени
  (τ = 80 мс) и по частоте (1/6 октавы).
- Когерентность `coh = |X| / √(P_L·P_R)`, `ILD = 10·log10(P_L/P_R)`.

### 7.2 Маска рассеянного `m(k,t)` (этап E)
1. База: `m0 = clamp((1 − coh − c0)/(1 − c0), 0, 1)`, `c0 = 0,3`.
2. Разведённые источники: `m1 = m0 · clamp((ild_direct − |ILD|)/ild_ramp, 0, 1)`, 12 / 6 дБ.
3. **Защита по энергии**: для полос 1/3 октавы — бегущий пик мощности за 1 с. Если мощность бина ниже пика полосы на
   60 дБ или ниже −90 dBFS → `m = 0`. Тишина — не «рассеянное».
4. **Атаки с заглядыванием**: детектор атак по полосам 1/3 октавы (положительный спектральный поток выше порога
   `median + 4·MAD` за 2 с). Если в полосе есть атака в пределах следующих **50 мс** (заглядывание обеспечено
   задержкой процессора) → `m` этой полосы → 0 заранее. После атаки подъём с τ = 150 мс. Спад — мгновенный.
5. Ниже 300 Гц `m = 0`.
6. Для слоя глубины `m_d` — `m` дополнительно сглаженная по частоте окном 1/3 октавы.

### 7.3 Слой ширины (этап D) — меняет только S
- `G_w2(k)`: 1 ниже 300 Гц; `g_mid` в 300 Гц – 5 кГц; `g_hi` выше 5 кГц; переходы — полукосинус 1/3 октавы.
- Рассеянное: `G_w = G_w2 · (1 + (g_amb − 1)·m)`.
- Разведённые источники: `G_w ← 1 + (G_w − 1)·clamp((ild_direct − |ILD|)/ild_ramp, 0, 1)`.
- **Ограничитель фазовости**: `G_w ← max(1, min(G_w, κ·√(P_M/P_S)))`, κ = 1,0. Не сужает исходник.
- `S′ = G_w · S`. Маска когерентности на `G_w2` **не** накладывается (ошибка 0.1.x: гасила эффект).
- Сглаживание `G_w` по времени — не быстрее 20 мс (против модуляции).

### 7.4 Слой глубины (этап F) — меняет только M
- `G_d = 1 − (1 − g_d(k))·m_d`, `g_d(k)` = `depth_db` (по умолчанию −2 дБ) плюс полка `−2 дБ` выше 8 кГц (D3,
  плавный переход 1 октава). `M′ = G_d · M`.

### 7.5 Синтез
`L′ = M′ + S′`, `R′ = M′ − S′` → ISTFT → перекрытие-сложение.

### 7.6 Отражения в Side (этап G)
- После ISTFT, во временной области, каузально: `s = (L_in − R_in)/2`, выровненный по времени с выходом;
  `r(t) = Σ a_i · BP(s)(t − τ_i)`, BP — полоса 500 Гц – 6 кГц (биквады 2-го порядка, каузальные), отводы из профиля
  (3–4 шт., 7–25 мс, −18…−14 дБ).
- `L′ += r`, `R′ −= r`. Моно не меняется по построению; чистый центр (s = 0) → r = 0.

### 7.7 Защита уровня и честное сравнение (внутри `SpatialSource`)
- **Связанный стерео-ограничитель** на выходе процессора (одно усиление на оба канала — не сдвигает сцену):
  порог **−0,3 dBFS** (R13: мастеринг музыки доходит до −0,1 dBFS; порог −1 дБ поджимал бы пики, которые были и
  без обработки, и A/B сравнивало бы ещё и компрессию), заглядывание 5 мс (входит в задержку процессора), восстановление 80 мс. Нужен потому, что
  отправка на Point переводит в int16 с обрезкой (`packet()` → `coerceIn`), а усиление Side может поднять пики.
  Ограничитель эквалайзера на рендере остаётся последней защитой.
- **Компенсация громкости**: процессор оценивает громкость (K-взвешивание BS.1770, скользящее окно 3 с) входа и
  выхода и применяет медленное общее усиление (τ = 10 с, пределы ±3 дБ), чтобы включение обработки не делало звук
  громче. Стробирование как в BS.1770 (абсолютный порог −70 LUFS, относительный −10 LU): тихие места и паузы не
  раскачивают оценку. В обычном режиме — настройка «Сохранять громкость», вкл.
- **В слепом A/B (R5) усиление компенсации замораживается** на всё время серии: значение, накопленное за последние
  10 с перед началом, применяется к обработанной ветке постоянным; ветка без обработки — без изменений. Иначе после
  каждого переключения громкость «доплывала» бы и выдавала вариант.

### 8.0 Всё определяется автоматически (принцип п. 0.2)
- **Таблица устройств** `assets/device_speakers.json`: модель (`Build.MODEL`) → `{stereoSpeakers, spacingM,
  rotationHandledBySystem, xtcVerified}`. Начальные записи: Xiaomi 14 Ultra (стерео; расстояние между динамиками
  измеряем мы при разработке; XTC — после нашей проверки), Redmi 14C (моно). Таблицу пополняем мы, не пользователь;
  она обновляется вместе с приложением.
- **Модель не в таблице**: стерео — если у `AudioDeviceInfo` типа `TYPE_BUILTIN_SPEAKER` `channelCounts` содержит 2;
  расстояние — 0,14 м; XTC — **выключен** (только ширина и глубина). Иначе — моно, профиль `off`.
- Выход звука (динамик / проводные / BT) — из текущего маршрута `AudioManager`; наушники и BT → `off`.
- Пара — по умолчанию `pair_wide`; `pair_near` — вручную в «Свой» (п. 9.2), без вопросов при подключении.
- Никаких сообщений «у вашего телефона моно-динамик» и т. п.: неподходящая функция просто не показывается.

### 8.1 Ориентация телефона в соло (R4)
- Встроенные стереодинамики при повороте телефона на 180° меняются местами. Для ширины это зеркалит сцену, для XTC —
  разрушает эффект.
- Ориентация — из поворота дисплея (`Display.rotation`), при заблокированном повороте — из датчика ориентации.
  Если `rotationHandledBySystem = false` — приложение само переставляет L/R на выходе так, чтобы левый **по положению**
  динамик получал L; если `true` (система делает это сама, как у многих Xiaomi) — не трогает. Смена ориентации —
  перекрёстное затухание 50 мс, без перезапуска процессора.
- Модель не из таблицы: флаг считается `true` (современные Android-устройства обычно переставляют каналы сами), XTC
  выключен (п. 8.0), ширина работает.
- Портретная ориентация → профиль `off`, молча; вернули альбомную → профиль включается обратно.

### 8.2 Системные эффекты производителя (R6)
- На Xiaomi по умолчанию включены Dolby Atmos / «Улучшение звука»; они обрабатывают выход приложения поверх нашей
  обработки. Приложение не может надёжно узнать, включены ли они, и **не просит пользователя их выключать**.
- Вместо этого: в телеметрию — модель и список эффектов системы (`AudioEffect.queryEffects()`), событие
  `SYSTEM_EFFECTS_SEEN`. Мы проверяем сочетание сами (на своих телефонах, в режиме разработчика, с эффектами вкл/выкл);
  если сочетание звучит хуже — в таблице устройств для модели ставится более мягкий профиль по умолчанию или XTC не
  включается (`xtcVerified = false`).

## 9. Этап J — интерфейс

### 9.1 Для пользователя — только наслаждаться
- Карточка Sound: строка **«Пространство»** с переключателем прямо в карточке: Выкл / Мягко / Сильно. Больше ничего
  выбирать не нужно — расстановка, стереодинамики, ориентация, XTC определяются сами (п. 8.0–8.1).
- Строка **не показывается**, если текущему выходу обработка не подходит (наушники, моно-динамик, портретная
  ориентация, Amplifier) — без пояснений и неактивных кнопок.
- В паре доступно на обоих телефонах (команды идут на Server, как у громкости). Телефон с моно-динамиком в паре
  играет свой канал как обычно — он полноценный участник сцены.
- Если второй телефон старой версии (нет `spatialV1`) — строка в паре скрыта.

### 9.2 «Свой» — для любопытных (необязательно)
Долгое нажатие на строку «Пространство» → экран `Sub.SPATIAL`:
- ползунки **Ширина** (g_mid и g_hi вместе), **Воздух** (g_amb), **Глубина** (depth_db), **Отражения** (уровень);
  в паре — «Телефоны рядом» (профиль `pair_near`); сброс к профилю;
- **живая визуализация сцены**: анимированная «ширина» по корреляции L/R и Side/Mid выхода — это удовольствие
  смотреть, а не прибор; чисел нет.
Ни проверок, ни тестов здесь нет.

### 9.3 Режим разработчика (скрыт; для нас, не для пользователя)
Включается 7 нажатиями на номер версии в Diagnostics (как в Android). Всё ниже в обычном интерфейсе не появляется:
- **Замер синхронизации** (п. 5).
- **Слепое сравнение A/B**: серия из 8 попыток, 6 — «обработка / без обработки» в случайном порядке, 2 контрольные
  (A = B); громкость выровнена и заморожена на серию (п. 7.7); ответы по атрибутам «Ширина», «Центр»,
  «Естественность»; итог с биномиальной вероятностью угадывания; сравнение двух настроек (Мягко против Сильно).
  Результаты — в `files/spatial_ab/*.json` и телеметрию (`SPATIAL_AB_TRIAL`, `SPATIAL_AB_RESULT`).
- **Старый корректор** (п. 4.4).
- **Отчёт XTC**: расчётное подавление (медиана и худшая точка) на проверочной сетке (п. 10.2).
- **Запись таблицы устройств** для текущего телефона (стерео/моно, расстояние, флаг ориентации, `xtcVerified`) с
  переопределением и короткий звук «L затем R» — для нашей проверки при добавлении модели в таблицу.
- Числа сцены: корреляция L/R по полосам, Side/Mid, `DSP_VERSION`, версии профилей и таблицы.

## 10. Этап I — XTC на одном телефоне (соло)

### 10.1 Модель и расчёт на телефоне
- Геометрия — из таблицы устройств (`spacingM`), слушатель по центру. Пользователь ничего не вводит.
- Модель: точечные источники, сферическая голова (радиус 8,75 см, аналитическая модель рассеяния), скорость звука
  343 м/с.
- **Расчёт на область**, покрывающую обычные положения (телефон в руке или на столе): дистанции 0,3–0,7 м шагом
  10 см × смещения −5/0/+5 см. Для каждого бина (БПФ 4096) — матрица 2×2 передачи «динамики → уши» на каждой точке
  сетки; фильтр `C(k)` — регуляризованное решение наименьших квадратов, минимизирующее перекрёстный путь по всей сетке
  при сохранении прямого: `C = argmin Σ_p ||H_p·C − D||² + β||C||²`, `D` — прямой путь с модельной задержкой,
  перекрёстный = 0. β — из профиля; «Мягко / Сильно» меняют β (сильнее эффект — меньше β).
- Рабочая полоса 500 Гц – 6 кГц; вне её `C` плавно переходит в единичную матрицу (полукосинус 1/3 октавы).
- Переход в КИХ: ОБПФ, окно Тьюки, 1024 отвода, **модельная задержка ровно 10 мс**, учтённая в задержке процессора
  (выход выровнен по времени со входом, п. 6.1). Расчёт — в фоновом потоке при смене уровня или модели, ≤ 200 мс на
  14 Ultra; результат кэшируется по `(модель, уровень)`.
- Применение — 4 свёртки (2×2) методом перекрытия-сохранения внутри `SpatialSource`, после слоя отражений и до
  ограничителя.
- XTC включается автоматически в профиле `solo_stereo_speaker` только при `xtcVerified = true`.

### 10.2 Проверки (наши)
- Импульс, модель без перекрёстного пути → выход совпадает со входом по времени ±1 сэмпл (баг прототипа: двойная
  задержка 30 мс).
- Отчёт в режиме разработчика: расчётное подавление перекрёстного пути (медиана и **худшая** точка) на проверочной
  сетке 0,3–0,7 м шагом 2,5 см × ±8 см шагом 1 см, отличной от сетки расчёта.
- Без измерительного микрофона реальные передаточные функции динамиков не измеряются; решение `xtcVerified = true`
  для модели мы принимаем по слепому сравнению в режиме разработчика.

## 11. Протокол, хранение, телеметрия

### 11.1 Протокол
- Команда `cmd a="spatial"` `{enabled, level, custom:{…}, placement, finished}` — путь как у `vol`/`eq`
  (`sendGainCommand`), Server применяет и публикует `"spatial"` в `state`. Point показывает, но звук не
  обрабатывает (получает уже обработанный канал).
- Capability `spatialV1`: Server включает обработку в паре только если она есть у Point — иначе Point старой версии не
  умеет перезаписывать TCP-буфер (п. 6.4). Без неё строка «Пространство» в паре скрыта (п. 9.1), без сообщений.
- Формат аудиопакетов не меняется.

### 11.2 Хранение
Пара — `PairRecord.spatial`; соло — по выходу звука (как профили эквалайзера); A/B — файлы п. 9.3.

### 11.3 Телеметрия
`SPATIAL_CONFIG` {profile, level, params, dspVersion, profilesVersion} — по `finished`;
`SPATIAL_PERF` раз в окно {rtFactor, cacheAheadMs, restarts, misses, limiterDb, loudnessCompDb, sideMidDb, corrMin};

## 12. Тесты (JVM, `src/test`)

### 12.1 Инварианты (перенос `tz-spatial-proto-0.2.md` §6, на потоковой реализации)
На сигналах: синтетические «музыкоподобные» сигналы, генерируемые в тесте (сумма гармонических тонов с атаками +
реверберация шумовым хвостом, разные панорамы) — **музыку с авторскими правами в репозиторий не класть** (R10);
настоящая музыка проверяется только локально задачей п. 12.5 и `evaluate_algorithms.py`;
шумы с корреляцией 0/0,25/0,5/0,75/1, центральная и стерео атака после тишины, разведённые источники, тишина.
1. Слой ширины + отражения, без глубины: `max|(L′+R′) − (L+R)|` ≤ −120 дБ от пика входа (float → допускается −110 дБ,
   если упирается в точность; зафиксировать).
2. Центральный вход → `|L′−R′|` ≤ −110 дБ.
3. Глубина: Side не меняется (≤ −110 дБ); форма моно по Велчу после вычитания гладкой составляющей ≤ 1,5 дБ пик-пик.
4. Предзвон: энергия до атаки ≤ −50 дБ от пика атаки.
5. Фазовость: корреляция L/R по полосам 1/3 октавы ≥ min(0, входная).
6. Разведённый источник: свой канал ±0,5 дБ, противоположный ≤ −30 дБ.
7. Ограничитель: пик ≤ −1 dBFS; компенсация громкости: |ΔLUFS| ≤ 0,5 после установления.

### 12.2 Потоковые свойства
1. Размер блока потребителя 1, 97, 480, 4096 → побитово одинаковый выход.
2. `sample()` в произвольном порядке (как у нескольких потребителей) = последовательному чтению.
3. Перезапуск с `F` после разогрева совпадает с непрерывной обработкой ≤ −60 дБ.
4. Смена параметров: перекрёстное затухание без скачков (максимальная разность соседних сэмплов ≤ 1,05 от входной).
5. Обход (`enabled=false`) = вход побитово.
6. Выход выровнен со входом: импульс → пик на том же кадре.

### 12.3 Коррекция и замер
Тесты п. 4.5 и п. 5.

### 12.4 XTC
Тест п. 10.2 (выравнивание); при β → ∞ фильтр → единичный; подавление на сетке расчёта ≥ модели прототипа.

### 12.5 Обработка WAV на Mac (вместо выгрузки из приложения)
Задача Gradle `:app:spatialRender` (или отдельный модуль `dsp` + `application`): `--in трек.wav --level soft|strong
--profile pair_wide|… --out папка`. Запускает **тот же** `SpatialSource`/`dsp` на JVM быстрее реального времени,
пишет `REF` и обработанные варианты в раскладке `render.py` (`tracks/*.wav`, `key.json` с `dsp_version`) — для
`evaluate_algorithms.py` без его изменений. Телефон и пользователь не нужны.

## 13. Производительность (Redmi 14C — нижняя граница, Xiaomi 14 Ultra)
- `SpatialSource` ≥ 20× реального времени (одно ядро) на Redmi 14C; XTC (только 14 Ultra) — ≥ 10×.
- Рост недоборов рендера за 30 мин с обработкой — 0; потребление батареи за 30 мин — не больше +5 % к без обработки
  (замер по `BatteryManager`, в телеметрию).
- Память: кэш 15 МБ + буферы; без выделений в рабочих циклах (проверить профилировщиком аллокаций один раз).
- **Автоматическое отключение при перегрузке (R8)**: если скорость процессора < 3× реального времени дольше 5 с или
  воспроизведение догнало `processedHead` (недобор из-за процессора, не декодера) — обработка переходит в обход через
  п. 6.4, молча, без сообщений пользователю; телеметрия `SPATIAL_AUTO_BYPASS`. Повторная попытка — автоматически
  со следующего трека; после трёх перегрузок за сеанс — обход до перезапуска приложения. Переключатель у пользователя
  остаётся в прежнем положении.

## 15. Приёмка (ручная, на паре Xiaomi 14 Ultra + Redmi 14C)
1. S1: индикатор L/R в мкс, p95 ≤ 20 мкс за 30 мин; «Замер синхронизации» даёт σ/p95; щелчков от коррекции нет.
2. S2: обработка-«единица» включена — задача п. 12.5 на WAV даёт выход, совпадающий с исходником ≤ −100 дБ (слепого A/B на этом
   этапе ещё нет — R2); на паре на слух и по `sync_probe` без изменений; перемотка/смена трека — старт без задержки > 150 мс; TCP-путь: смена параметра слышна на Point
   через ~0,6 с, без паузы.
3. S3: в режиме разработчика числа сцены показывают рост Side/Mid (+1,5…+3 дБ на джазе при «Мягко»), корреляция ≥ 0; моно проверяется
   задачей п. 12.5 + `evaluate_algorithms.py` — без нарушений.
4. S4: задача п. 12.5 на джазовых фрагментах + `evaluate_algorithms.py` — все инварианты; на слух — нет «ванной», атаки чистые.
5. S5: 8 попыток A/B проходятся за ~5 мин, итог и p-value сохраняются.
6. S7: на 14 Ultra в соло, альбомная ориентация, «Мягко/Сильно» — XTC включается сам (после `xtcVerified`); слепое A/B
   в режиме разработчика; при смещении головы на ±10 см звук не разваливается; поворот на 180° — сцена не зеркалится.
7a. Пользовательский интерфейс: ни одного теста, вопроса, подтверждения или выгрузки; на Redmi 14C в соло строки
   «Пространство» нет, в паре он играет свой канал; всё из п. 9.3 без режима разработчика недоступно.
7. Везде: калибровка, метроном, проверка каналов — звучат без обработки; Amplifier — без обработки.
