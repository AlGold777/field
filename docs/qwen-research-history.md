# Хронология исследования Qwen и инженерной работы в SoundField Research

**Для:** руководства SoundField
**Дата составления:** 27 октября 2026 г.
**Часовой пояс:** Europe/Madrid (CET, UTC+1 в даты журнала 26–27 октября)
**Предмет:** исследовательские чаты Qwen в Chrome и инженерная сессия «ТЗ Qwen» проекта Gemini/Antigravity `SoundField Research`
**Статус документа:** реконструкция истории по видимым перепискам, машинному журналу Gemini и артефактам проекта. Это не повторная техническая экспертиза аудиостека.

## Краткое резюме для руководства

Работа прошла три смысловых этапа. Сначала Qwen рассмотрел общий захват системного аудио и Bluetooth, затем пользователь уточнил конкретную цель: взять Spotify, разложить стерео на L/R, передать только один канал по Bluetooth и воспроизвести второй на телефоне. В ответ Qwen перечислил блокеры (доступ к PCM, подавление исходного звука, независимые выходы, гарантии канала у обычного BT-приёмника и синхронизация) и предложил трёхдневную последовательность проверок. После этого Qwen сформировал исследовательское ТЗ с ролями, волнами, матрицей применимости Android/OEM и критериями доказательности.

В инженерной сессии Qwen в Gemini сначала возникло расхождение постановки: начальный шаблон реконструировал критерии для общего системного аудио → Bluetooth, а затем инженерное ТЗ описывало общий `Audio Router`, а не только строгий сценарий Spotify L/R. В проекте появился многомодульный Android APK на базе MediaProjection/AudioPlaybackCapture и Native DSP/Oboe. Первая сборка Gradle завершилась ошибкой CMake из-за отсутствующего исходника; после исправлений APK был собран. Позднее по пользовательским запросам появились диагностические логи, копирование `Log ⧉`, разные версии `0.100`, `0.101`, `0.102` и постоянная первая строка лога.

**Подтверждено журналом:** инженерный проект собран как минимум в debug APK; `assembleDebug` для `0.100`, `0.101` и `0.102` завершился успешно. Строка `=== Qwen AudioSplit Log Initialized ===` найдена внутри APK `0.102`. **Не подтверждено журналом:** установка и запуск на физическом телефоне, захват реального Spotify, L/R-разделение на выходах, отсутствие утечки, одновременное воспроизведение BT + динамик, задержка/дрейф и A/V sync. Табличные статусы `PASS` в исследовательском ответе Qwen следует считать содержимым ответа, а не протоколами испытаний: доступный инженерный журнал не содержит соответствующих измерений с Pixel/Samsung/Xiaomi.

## 2. Исходная цель и изменение рамки

### 2.1. Первый запрос Qwen в Chrome

Пользователь попросил разработать способ захватывать системный звук мобильного телефона и передавать аудиопоток через Bluetooth. Первый ответ Qwen самокритично перечислил слепые зоны первоначального решения: DRM и opt-out, отсутствие гарантированного одновременного вывода на динамик и BT, роль LE Audio/Auracast и неоднозначность слова «парсинг». Затем Qwen предложил три направления: внешний аппаратный адаптер, модификацию HAL для системного/корпоративного решения и событийный Edge AI. В рамках целевого продукта это были альтернативные направления, а не выполненная реализация; аппаратный адаптер и HAL меняют исходные ограничения.

### 2.2. Пользователь уточнил требование

Пользователь сузил задачу: поток именно Spotify, разделить стерео на два канала, один L или R отправить по Bluetooth, второй оставить на динамике телефона; отдельно попросил рассуждать как инженер октября 2026 года и рассмотреть новые алгоритмы. Qwen ответил, что на обычном Android/iOS при неизменённых условиях не видит надёжного легального универсального пути. В качестве главных технических рисков названы:

- источник может запрещать AudioPlaybackCapture или выдавать тишину для защищённого контента;
- уменьшение общей громкости может одновременно убрать и оригинал, и захваченный сигнал;
- публичный API не гарантирует два независимых физических выхода одновременно;
- стандартный BT-приёмник может смешать каналы или не подтверждать воспроизведение только L/R;
- дополнительная задержка не управляется сторонним видеоплеером и осложняет синхронизацию.

Qwen набросал исследовательские проверки и алгоритмические направления: отличать тишину источника от блокировки по RMS/MediaSession/длительности, оценивать задержку и дрейф двух веток, изучить AV-компенсацию и способы подавления оригинала. Qwen сам указал, что оценка задержки без обратной связи от приёмника остаётся оценкой, а не гарантией; некоторые желаемые функции не имеют устойчивого решения без системной интеграции или сотрудничества источника/приёмника.

### 2.3. ТЗ на исследование по ссылке пользователя

Следующая видимая постановка просила Qwen быть руководителем исследования: раздать гипотезы/маршруты/допущения агентам, потребовать границы применимости по Android 13–16/OEM/API, первичные источники, явное различение подтверждения/вывода/гипотезы, отрицательные вердикты только с доказательством, адвокатскую проверку, инженерные эксперименты, картографа, видео- и алгоритмический блоки, синтезатора, волны, возвраты и критерии приёмки. В запросе также требовалось не проводить само исследование, а выдать ТЗ.

Ответ Qwen прямо отметил, что в данном чате предыдущего ответа нет, поэтому шесть условий и набор гипотез реконструируются. Затем он создал реестр гипотез и допущений, девять ролей исследователей/синтезатора, план координации и критерии отчёта. В том же ответе присутствовали следующие крупные секции: «акт приёмки и директива», «инженерный пакет: архитектура и прототип», затем полное ТЗ на разработку APK с Kotlin/C++/Oboe, тестированием, дорожной картой и таблицей hardware-тестов. Таблица содержит примеры со статусом `PASS` (Pixel 8, Samsung S23, Xiaomi 13, Netflix/DRM); в исследованном журнале Gemini нет сырых логов этих устройств. Поэтому это не следует представлять руководству как свершившиеся испытания.

## 3. Хронология инженерной сессии Gemini/Antigravity

### 26 октября 2026 г.

#### 13:18 — старт чата «ТЗ Qwen» и реконструкция рамки

В первой записи пользователь передал исследовательское задание по маршрутам захвата системного аудио и передачи на Bluetooth для Android 13–16. В самом тексте были заданы реконструированные C1–C6 для общего маршрута системного аудио → BT, гипотезы `GPT-H1…H12`, роли и условия отчёта. Указание пользователя: в предыдущем ответе данного диалога нет, значит рамку нужно реконструировать и пометить как вывод, а расхождения позже переоткрыть.

Журнал показывает, что агент прочёл и создал `STEREO_SPLIT_RESEARCH_SPECIFICATION.md` (416 строк, около 48.8 KB), а затем сформировал исследовательский синтез. В первом крупном отчёте заявлены 15 маршрутов и широкие охваты Android 13–16, OEM, AOSP, LE Audio и экспериментов. Это содержимое отчёта модели; само наличие документа не означает, что каждая заявленная проверка действительно проводилась. На раннем шаге также возникло расхождение: исследовательская рамка сформулирована как «общая системная маршрутизация → Bluetooth», тогда как целевая задача Chrome уже была про Spotify L/R → BT + динамик.

#### 13:28 — пользователь требует довести отчет до критериев завершённости

Пользователь настоял на автономном завершении без промежуточной остановки. Были перечислены критерии: вердикт каждой гипотезы, минимум три варианта, заполненная матрица Android/OEM, пакеты испытаний для всех непроверенных ячеек, блокеры/закрытые обходы/условие пересмотра, юридические параметры, точный реестр проверенных источников, самоаудит. Непроверяемое без телефона нужно оформить как `ТРЕБУЕТ УСТРОЙСТВА` и приложить эксперимент до одного дня. Требовалось вернуть только полный итог из 11 разделов. Эта длинная пользовательская инструкция приложена дословно в разделе 7.

После этого в журнале записана новая версия итогового отчёта. Статус «исследование завершено» в ответе Qwen/Gemini не принимается здесь как доказательство аппаратных испытаний: отдельные журналы физических устройств отсутствуют.

#### 14:18 — пользователь передаёт ТЗ на APK «Audio Router»

Новая постановка изменила ближайший результат: production-oriented APK/AAB для системной маршрутизации аудио в пределах Android sandbox. В техническом ТЗ зафиксированы C1–C6: Android 13–16; кросс-OEM без vendor API; non-root без shell/Shizuku/hidden API; соблюдение Play/ToS и системный MediaProjection consent; без модификации чужого APK; целевая задержка ≤100 мс и допуск ≤200 мс, DSP на C++/Oboe. Были заданы Kotlin/C++17, Gradle/AGP/CMake, модули, интерфейсы AudioEngine/State, native ring buffer, SPLL, арбитраж маршрутов, fallback, UI/permissions и QA.

В ответ инженерный агент представил план разработки и принял ТЗ. Важно: это ТЗ формулирует общий Audio Router; оно не отменяет исходного требования Spotify L/R на BT и speaker и не свидетельствует, что весь этот сценарий достигнут. Полный исходный запрос в приложении.

#### 14:04–15:15 — создание проекта и первая сборка

По машинному журналу проект сформирован в каталоге `Qwen/` как многомодульная структура. Проверена среда: OpenJDK 17, Android SDK/NDK, Gradle 8.9; проект использует AGP 8.5.2, Kotlin 1.9.24 в конфигурации, `compileSdk 35`, `minSdk 33`, `targetSdk 35`.

В процессе поиска способа подключения Oboe были проверены URL Maven Central для версий 1.8.1 и 1.9.0 — оба вернули HTTP 404; поиск метаданных на Maven Central также не нашёл артефакт. В журнале затем проверен Google Maven и официальный README/Getting Started Oboe. Это было препятствием конфигурации зависимости, а не результатом аудиотеста.

Первый `./gradlew assembleDebug` для `Qwen` завершился `BUILD FAILED` за 1 мин 9 с. Причина из CMake: `Cannot find source file: src/AudioEngine.cpp` и `No SOURCES given to target: audio_router_dsp`. После проверки путей обнаружились C++ файлы в `native-dsp/src/main/cpp/src/`, тогда как CMake ожидал другой относительный путь. Далее журнал показывает изменение CMake/файлов и повторную сборку. В `app/build/outputs/apk/debug/` появился `app-debug.apk`; проверка содержимого увидела DEX и библиотеки `libaudio_router_dsp.so`, `liboboe.so` для ARM64 и x86_64. Файл был скопирован как `Qwen/audio-router-debug.apk` размером около 10.95 MB. Это подтверждает упаковку библиотеки в APK, но не её фактическую работу на устройстве.

#### 15:26 — именование APK по модели и версии

Пользователь указал точное имя `app-debug-qwen-0.100.apk`. В тот момент уже существующий debug APK был скопирован под этим именем; затем Gradle конфигурация обновлена и сборка повторена. Журнал подтвердил наличие файла в корне `Qwen/` и каталоге Gradle outputs. Позднее пользователь отдельно обратил внимание, что инкрементальные версии должны отличаться содержимым и номером, а не только именем.

#### 16:06 — вопрос о передаче канала на второй телефон

Пользователь спросил: «А если я хочу раздать один канал на другой мобильный телефон». Ответ Qwen рассмотрел второй телефон как дополнительное устройство/приёмник и варианты сетевой/Bluetooth передачи с клиентом на второй стороне. Это расширение выходит за первоначальное строгое условие «решение на одном телефоне, без второго посредника». В доступном журнале для этой функции не зафиксированы реализация, тест или отдельный APK; вопрос учтён как исследованное направление, а не готовая функция.

## 4. ЛОГИКА АРБИТРАЖА И FALLBACK (Graceful Degradation)

**Класс `RouteArbitratorImpl` (в модуле `data`):**
```kotlin
class RouteArbitratorImpl @Inject constructor(
    @ApplicationContext private val context: Context
) : RouteArbitrator {
    override fun determineStrategy(): RoutingStrategy {
        val btManager = context.getSystemService<BluetoothManager>()
        val adapter = btManager?.adapter ?: return RoutingStrategy.DIRECT_PASSTHROUGH

        // Ветвление по API Level
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.UPSIDE_DOWN_CAKE) {
            if (adapter.isLeAudioBroadcastSourceSupported == BluetoothStatusCodes.FEATURE_SUPPORTED) {
                return RoutingStrategy.LE_AUDIO_BROADCAST
            }
            if (adapter.isLeAudioSupported == BluetoothStatusCodes.FEATURE_SUPPORTED) {
                return RoutingStrategy.LE_AUDIO_UNICAST
            }
        }
        return RoutingStrategy.A2DP_CAPTURE
    }
}
```

**Обработка Fallback (Алгоритм 4):**
При получении `EngineState.FallbackTriggered` сервис обязан:
1. Вызвать `audioEngine.stopCapture()`.
2. Через `AudioManager.setPreferredDeviceForStrategy()` перенаправить системный `STRATEGY_MEDIA` напрямую на BT-устройство.
3. Обновить Notification: "Protected Content - Direct Passthrough Active".
4. **НЕ ПЫТАТЬСЯ** перезапустить захват, пока пользователь явно не остановит и не запустит сервис заново.
