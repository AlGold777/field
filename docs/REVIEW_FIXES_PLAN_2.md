1. Старт: `git switch -c fix2/<ID> claude/review-fixes`. Только эта база. План читать из этого файла в своей ветке.
2. Менять только файлы из своего списка «Владеет». Найденное вне списка — в отчёт.
3. Не трогать версии (`versionName`, `versionCode`, `MARKETING_VERSION`, `CURRENT_PROJECT_VERSION`) и документацию — это делает ведущий.
4. Один пункт — один коммит, `git add <пути>`; сообщение `<ID>-<N>: …`, последняя строка `Co-Authored-By: Claude Haiku 5.5 <noreply@anthropic.com>`.
5. Перед правкой убедиться, что дефект есть **в текущем коде**. Нет — не править, записать «не подтверждено» и почему.
6. Минимальный дифф, стиль и язык комментариев окружающего кода. Не менять протокол и константы.
7. **Продуктовые документы обязательны:** `docs/player-upper-controls.md`, `docs/player-stage-layout.md`, `docs/player-prototype-rollout.md`, `docs/audio-algorithms.md`. Если пункт плана противоречит им — документ главнее, пункт не делать, записать в отчёт. Принцип продукта: пользователь только слушает; никаких новых подсказок, тестов, подтверждений и экранов настройки в обычном UI; вёрстка верхней части плеера не должна сдвигаться.
8. **Проверка (обязательна, результат — в отчёт дословной последней строкой вывода):**

   - Проверку прогонять после каждого коммита, затрагивающего код. Красная проверка = коммит исправить, а не идти дальше.
9. Новые тесты Android — JUnit в `android/app/src/test/java/app/soundfield/...` по образцу существующих (`PlayoutCorrectorTest.kt` и др.).
10. Отчёт (до 40 строк): коммиты (хеш, пункт), «не подтверждено/не сделано» с причиной, последние строки проверок, что осталось непроверенным (поведение на устройстве).

## K — ядро: калибровка и приём (обе платформы)

**Владеет:** `android/.../core/Calibration.kt`, `core/PointReceiver.kt`, `ios/SoundField/Core/Calibration.swift`, `Core/PointReceiver.swift`, новый тест `android/app/src/test/java/app/soundfield/core/CalibrationPeakTest.kt`.

- **K-1.** `findPeak` (обе платформы): текущий «первый локальный максимум ≥ 50%» работает по |вещественной корреляции|, которая осциллирует с несущей чирпа (1,5–7,5 кГц): соседние лепестки ±5 сэмплов имеют уровень 60–90% пика, поэтому выбирается лепесток на 0,1–0,3 мс раньше истинного. Заменить на: `i0` — первый индекс окна, где `c[i] ≥ 0.5·maxV`; `best` — argmax `c` на `[i0, min(to, i0 + round(0.001·sr))]` (1 мс — главный лепесток прямого пути; отражения позже 1 мс не выбираются). Остальное (порог отношения 8, параболическая интерполяция, окно) не менять. Kotlin и Swift — идентично.
- **K-2.** JUnit `CalibrationPeakTest.kt` через публичный `CalibrationAnalyzer.analyze` и `Chirp.make`: (a) чистый сигнал с известной задержкой — ошибка < 0,05 мс; (b) отражение сильнее прямого (×1,5) через 9 мс — измеряется прямой путь (ошибка < 0,1 мс); (c) отражение слабее прямого (×0,3) раньше на 3 мс — игнорируется; (d) тишина и только шум — `ok == false`. Синтез записи — по образцу `android/coretest/CoreSimulation.kt` (там есть генератор сценария калибровки) или ветки `fix/G` (`git show fix/G:android/coretest/CoreSimulation.kt`).
- **K-3.** `PointReceiver.swift`: вытеснение самого старого `pending` сделано `pending.min(by:)` — O(512) на каждый вставляемый seq. Сделать O(1) амортизированно: массив ключей в порядке вставки + индекс головы (ключи, уже удалённые из словаря, пропускать), как `LinkedHashMap` в Kotlin. Поведение и счётчики не менять.
