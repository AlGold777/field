# SoundField — стереопара из двух смартфонов (V1)

Два телефона с установленным SoundField объединяются в одну стереосистему: один играет левый канал, другой — правый.
Никакого внешнего оборудования — только программная синхронизация через Wi‑Fi. Пара может быть смешанной:
**Android + Android, iPhone + iPhone, Android + iPhone**. Базовые pairing и аудиопротокол совместимы между платформами;
передача музыки с Point на Server доступна только для пары Android + Android.

```

├── android/            Android Studio проект (Kotlin, Jetpack Compose, minSdk 26, targetSdk 35)
│   ├── app/src/main/java/app/soundfield/

│   │   ├── engine/     сессия пары: обнаружение, TCP/UDP, роли, команды, диагностика
│   │   ├── audio/      AudioTrack-выход с таймстампами, запись микрофона
```

## 1. Что умеет V1

| Возможность | Как реализовано |
|---|---|
| Поиск телефонов рядом | DNS‑SD / Bonjour `_soundfield._tcp` (Android NSD ↔ iOS NWBrowser) |
| Создание пары | приглашение с одного телефона → подтверждение на втором |
| Роли Server / Point | пригласивший — **Server** (ведёт плеер и общую шкалу времени), второй — **Point** |
| Каналы L/R | Server = L, Point = R по умолчанию; переключение нажатием на градиентную полоску между кругами или на сами круги L/R |
| Музыкальный плеер и очередь | Добавление нескольких файлов или целой папки нажатием на название трека; раскрываемый список очереди с выбором трека, автоматическим переходом и сохранением состояния списка |
| Импорт с Point | Android ↔ Android: файлы/папка передаются на Server с прогрессом; временные файлы удаляются при отмене или обрыве |
| Длинные треки | Android декодирует по 5-секундным сегментам, начинает после первого сегмента и ждёт готовые данные при медленном декодировании |
| Звук | Общая громкость, баланс L/R между телефонами и уровни каналов; цифровые настройки синхронизируются на оба телефона |
| Инструменты плеера | «Калибровка» и «Диагностика» стоят в одном компактном ряду с иконкой телеметрии |
| Синхронизация и доставка | TCP заранее передаёт Point 30 с его моно PCM16 канала; буфер 43,7 с, старт новой эпохи ждёт 500 мс данных (до 2 с), при сбое TCP используется UDP. Часы берутся из UDP, а при его потере — из TCP |
| **Калибровка задержки** | автоматическая по микрофону; «только измерить»; ручной сдвиг с метрономом; проверка каналов L/R |
| Разрыв пары | нажатие на индикатор «Стереопара активна» открывает подтверждение; после разрыва тот же индикатор становится кнопкой «Подключить» |
| Быстрое переподключение | сохранённая пара подключается без подтверждения; при обрыве переподключаются **оба** телефона (сначала по последнему IP, затем через mDNS); после перезапуска или возврата в приложение пара восстанавливается автоматически |
| Фон / выключенный экран | Android: foreground service `mediaPlayback` + Wake lock + Wi‑Fi lock `HIGH_PERF` (работает и при выключенном экране); iOS: `UIBackgroundModes=audio`, аудиодвижок работает всё время, пока телефон в паре; после сна пересоздаются TCP‑сервер и UDP‑сокет |
| Прерывания | звонок/другое приложение на любом телефоне → пауза всей пары (состояние остаётся согласованным) |
| Диагностика (Android 1.4.8) | JSONL-телеметрия, звуковой уровень на обоих выходах, буфер и путь аудио/часов, активные инциденты, число/время заморозок процесса, чёрный ящик на 120 с, объединённый экспорт пары Android; iOS делится текущей сводкой |

Вне V1 (по спецификации): 3+ устройств, пространственная карта, party/guest, live‑вход, захват звука чужих приложений.

## 2. Сборка

### Android
Текущая версия Android: **1.4.8** (номер сборки **22**); iOS: **1.1.7** (номер сборки **9**).
Android привязывает UDP к Wi‑Fi сети TCP-соединения, передаёт и сохраняет IPv4-адреса пары,
перебирает все известные адреса через доступные Wi‑Fi сети параллельно с интервалом 200 мс,
закрывает лишние соединения после первого успеха и предупреждает о нескольких активных Wi‑Fi.
Потеря сети текущего TCP-пути начинает восстановление пары сразу; при наличии Wi‑Fi новые серии начинаются
не реже чем раз в 3 с, при полном отсутствии Wi‑Fi — до 15 с. Через минуту без пары появляется `PEER_UNREACHABLE`.
При отсутствии звука UDP-медиасессия восстанавливается с эскалацией после трёх обновлений без отправленных аудиопакетов;
длинные файлы декодируются сегментами, а передача выбранных файлов с Point работает в паре Android ↔ Android. В iOS добавлена такая же диагностика
и процедура восстановления UDP; длинные файлы на iOS по-прежнему декодируются целиком.
Сборка Android и симуляционные JVM-тесты ядра проходят. Swift-файлы проверены на синтаксис.
Проверка воспроизведения, переподключения и передачи файлов требует двух физических Android-телефонов.

В предыдущей версии полоска между каналами выровнена по центрам кругов и переключает L/R; дублирующая кнопка удалена. Исправлено восстановление аудиовыхода:
ошибки записи, включая `ERROR_DEAD_OBJECT`, и отсутствие прогресса в течение 2 секунд приводят
к освобождению и пересозданию `AudioTrack` без разрыва пары. Повторная попытка — через 250 мс.
Временная шкала учитывает только принятые аудиоустройством сэмплы; недоступные, устаревшие
или некорректные таймстампы заменяются оценкой по текущему времени и позиции воспроизведения.
Это устраняет обнаруженные причины зависания вывода, но не заменяет диагностику потери UDP или аудиофокуса.

1. Android Studio Ladybug (2024.2) или новее, JDK 17.
2. `File → Open → SoundField/android`. Gradle‑wrapper 8.10.2, AGP 8.7.3, Kotlin 2.0.21 подтянутся сами.
3. `Run ▶` на двух реальных телефонах (эмулятор не подходит: нет mDNS между эмуляторами и реального звука).
   Командная строка: `cd android && ./gradlew assembleDebug` → `app/build/outputs/apk/debug/app-debug.apk`.
4. Регрессионные тесты аудиотайминга: `cd android && ./gradlew testDebugUnitTest`.
5. Тесты ядра без Android SDK: `android/coretest/run.sh` (нужен только Kotlin‑компилятор; путь задаётся `KOTLIN_LIB`).

### Телеметрия и адреса (Android 1.4.4, этап 1)

На Android кнопка **«Телеметрия»** есть на стартовом экране, экране плеера и экране диагностики; в плеере она показана иконкой. Экспорт создаёт новый
текстовый `.txt` в общей папке **Download** и открывает системное меню «Поделиться». В паре Android ↔ Android
получается один файл с `summary.txt`, состояниями обоих телефонов и их JSONL-журналами. Журнал второго телефона
передаётся порциями по TCP и собирается в локальном временном файле. Если второй телефон
недоступен или это iOS, сводка указывает причину и содержит журнал только текущего телефона. На Android 8–9
приложение запрашивает разрешение на запись; Android 10+ использует MediaStore.Downloads
([документация Android](https://developer.android.com/training/data-storage/shared/media)).

Журнал пишется в приватную папку приложения с момента запуска, переживает перезапуск и хранит до трёх файлов
по 2,5 МиБ каждый. Записи — JSON Lines со временем UTC и монотонным временем, ролью, коротким ID устройства,
версией приложения, категорией, важностью, контекстом пары и сессии, деталями и стеком ошибки (до 12 кадров).
События покрывают сеть и pairing, команды пользователя, декодирование, передачу файлов, калибровку,
переподключения и ошибки приложения. Каждую секунду сохраняется диагностический снимок в кольце на 120 секунд;
каждые 10 секунд журнал получает сжатые метрики. При инциденте, необработанном исключении, отметке проблемы
и экспорте кольцо сбрасывается как `BLACKBOX`.

В `WIFI_ADDRESSES` сохраняются IPv4 и IPv6 адреса каждого Wi‑Fi интерфейса. `TCP_OPEN`, `TCP_CONNECTED` и
`TCP_CONNECT_FAILED` содержат локальный адрес, сеть, Network ID и удалённый адрес; `UDP_SOCKET_BOUND` и
`SOCKET_BOUND` — интерфейс, адрес и порт сокета. `MULTI_WIFI` перечисляет активные Wi‑Fi сети и IPv4.
Версия протокола остаётся 1; Android объявляет `caps=["addrs","tcpClock","tcpAudio"]`. Возможности включаются только при их наличии у обеих сторон. `addrs` включает обмен адресами, `tcpClock` — резервную синхронизацию часов по управляющему TCP, `tcpAudio` — отдельный TCP-сокет с PCM16 каналом Point. Старая версия Android и iOS не объявляют новые возможности, поэтому продолжают использовать UDP без изменений. Поля `addrs` передаются в invite/accept/resume/session
и обновляются при изменении локальной сети. Старые Android и iOS игнорируют неизвестные JSON-поля и типы сообщений
(проверено по Android и Swift обработчикам); без совпадающих возможностей сохраняется прежний UDP-путь.
`CONNECT_CANDIDATES` содержит полный список попыток «локальная сеть → адрес второго телефона», их результат и
ошибки; `TCP_PATH_LOST` отмечает потерю сети активного TCP. `PEER_UNREACHABLE` и одноимённый инцидент
создаются после 60 секунд без восстановления и включают опробованные маршруты.
Снимки Point включают количество
отправленных PING и ошибок отправки. При отсутствии аудио Server обновляет UDP-сессию; после трёх обновлений
с нулём отправленных аудиопакетов он перепривязывает сокет к сети TCP-соединения. Если после ещё трёх обновлений
пакеты не отправляются, приложение показывает список Wi‑Fi сетей и продолжает восстановление раз в 30 секунд.

Отдельный TCP-аудиоканал поддерживает на Point до 30 секунд PCM16 моно с абсолютной нумерацией кадров, epoch и track ID; UDP остаётся путём для старых версий и iOS, а также резервом при недоступности TCP. При seek и смене трека новая epoch ждёт 500 мс непрерывного буфера или 2 секунды. `AUDIO_PATH`, `CLOCK_PATH` и `START_WAIT` фиксируют переключения; `POINT_BUFFER_LOW` срабатывает при запасе меньше 3 секунд дольше 5 секунд. Для часов Point выбирает UDP PONG, а после 1,5 секунды без PONG переключается на TCP ping/pong.

Когда временная шкала стоит на паузе 5 секунд, Android прекращает подавать тишину в AudioTrack и возобновляет его при получении новой играющей эпохи. Интервал heartbeat свыше 5 секунд записывается как `PROCESS_FROZEN` с состоянием до и после; накопленные число и длительность показываются в диагностике. После первого `PROCESS_FROZEN` или `PEER_UNREACHABLE` раз в сутки открывается экран стабильной работы со ссылкой на настройки приложения и рекомендациями HyperOS. При создании пары Android также предлагает системное исключение SoundField из оптимизации батареи.

На обоих Android-телефонах измеряются RMS/пик фактически выданного сигнала, темп аудиовыхода по таймстампу,
тишина от underrun, системная громкость и mute, маршрут, аудиофокус; Server измеряет канал Point из источника даже
при нулевой отправке UDP-пакетов. Диагностика показывает дБFS, активные инциденты и (в debug-сборке) переключатели
двух контролируемых сбоев. Правила включают потерю UDP-аудио, тишину выхода, остановку аудиотаймстампа,
mute, ошибку синхронизации, малый запас декодирования, зависшие декодирование/передачу, рассогласование
состояний, долгий цикл и молчащий TCP-канал.

Кнопка **«Здесь проблема»** на плеере и экране диагностики сохраняет необязательный комментарий, отправляет
одинаковую метку подключённому Android-телефону и сбрасывает чёрный ящик на обеих сторонах. В экспорте
сводка перечисляет устройства, версии, временной период, инциденты с длительностью и статусом, метки,
частые ошибки, ключевые счётчики, потери журнала и оценку смещения часов.

Тексты токенов маскируются; имена и URI аудиофайлов заменяются коротким SHA-256 и расширением. Ключ пары
и содержимое музыки не записываются. Телеметрия автоматически никуда не отправляется: передача журнала
возможна только по существующему TCP-каналу второго телефона Android. На iOS иконка делится краткой текстовой
сводкой текущего состояния пары и сетевых показателей через системное меню «Поделиться»; журнал событий iOS пока
не ведётся. Этап 1 не включает сбор ресурсов и причины прошлых завершений процесса (этап 2), полный журнал
телеметрии iOS и скрипт анализа (этап 3).
Ручная проверка на реальных телефонах ещё требуется.

## 3. Как пользоваться

1. Оба телефона — в одной сети Wi‑Fi (или один раздаёт точку доступа, второй к ней подключён). Открыть SoundField на обоих.
2. На телефоне A в списке «Телефоны рядом» нажать на телефон B → на B появится «Создать стереопару?» → «Принять».
3. A становится **Server (L)**, B — **Point (R)**. Поставьте телефоны: A слева, B справа, в 1,5–2 м друг от друга.
4. На Server нажмите название трека, чтобы выбрать несколько файлов FLAC, WAV, MP3 или папку. На Point в паре Android ↔ Android то же действие отправляет выбранные файлы на Server. В смешанной паре или при участии iPhone добавлять файлы можно только с Server. Первый импорт заменит демонстрационный источник; следующие добавятся в конец очереди. Раскройте список под кнопками плеера и нажмите трек для воспроизведения. Нажатие на текущий трек возобновляет его с паузы. Свайп по названию влево включает следующий трек, вправо — предыдущий; на границах очереди перехода по кругу нет. Point показывает ту же очередь и может переключать треки.
5. `▶` запускает текущий трек. Если очередь пуста, доступен встроенный тестовый трек: первые 4 секунды — «пинг‑понг» слева/справа, дальше: аккорды и бас слева, мелодия справа.
6. В блоке **Sound** настройте общую громкость и уровни L/R. Ползунок баланса перемещает звучание между телефонами; по центру оба канала звучат одинаково.
7. **Калибровка** → положить телефоны рядом → «Запустить автокалибровку» (~8 с тишины). После — расставить обратно.
8. Нажмите на индикатор «Стереопара активна» и подтвердите разрыв кнопкой «Да». Оба телефона остановятся; сохранённая пара останется на стартовом экране. Индикатор «Подключить» восстановит её без нового подтверждения.

Поддерживаемые форматы определяются системным декодером устройства. Android Server хранит доступ к выбранным локальным файлам; файлы, отправленные с Android Point, копируются в приватное хранилище Server. Декодированный PCM-кэш создаётся отдельно. Point получает очередь и команды, а звук передаёт Server.

## 4. Архитектура

### 4.1 Два контура связи
- **Управляющий (TCP, надёжный)**: pairing, роли, `state` плеера, `timeline` (эпохи), команды `cmd`, калибровка, диагностика, heartbeat.
  Кадр: `[u32 длина, big‑endian][UTF‑8 JSON]`.
- **Медиа (UDP)**: Server → Point PCM‑блоки по 10 мс (480 кадров, int16 моно — только канал Point) с номером кадра,
  моментом воспроизведения и моментом отправки; Point → Server `PING` (часы) и `NACK` (перезапрос потерянных).

### 4.2 Общая временная модель
Server задаёт **эпоху** шкалы: `кадр F звучит в момент anchorNs + (F − anchorFrame)/48000` по часам Server.
Любой play / pause / seek / смена каналов / тестовый режим создаёт новую эпоху с бо́льшим номером — пакеты старых эпох
распознаются как **устаревшие** и отбрасываются. Старт всегда назначается на `now + 300 мс`, чтобы Point успел получить данные.
Server отправляет аудио на **400 мс вперёд** — это запас jitter buffer и время на перезапрос потерь.

### 4.3 Часы: offset и drift (`ClockSync`)
Задержка в каждом направлении = физическая + очередь (≥ 0). Поэтому минимум задержки по **каждому направлению отдельно**
почти не содержит шума очередей:
`fwd = t2 − t1` (PING, Point→Server), `bwd = t4 − t3` (PONG **и каждый аудиопакет**, Server→Point),
`offset ≈ (min fwd − min bwd)/2`. Минимумы собираются в корзины по 2 с; по корзинам за ~80 с строится взвешенная
регрессия `offset(t) = a + b·t` → **drift** (ppm). PING — 20 раз по 50 мс при подключении, затем 5 раз/с.

### 4.4 Воспроизведение без рассогласования (`PlayoutCorrector`)
Каждый аудиоблок (5 мс) знает момент, когда его первый сэмпл выйдет из динамика:
- Android: `AudioTrack.getTimestamp()` → `present = ts.nanoTime + (записано − ts.framePosition)/SR`;
- iOS: `AudioTimeStamp.mHostTime` + `AVAudioSession.outputLatency`.

По этому моменту и часам Server вычисляется «идеальный» кадр. Сглаженная ошибка ≤ 0,125 мс игнорируется; больше —
пропуск или повтор **одного** сэмпла на блок (≤ 4 мс/с коррекции, на слух незаметно); > 20 мс — жёсткий прыжок.
Так компенсируются и дрейф кварцев аудиоустройств, и изменение задержки во времени. Point, кроме того, вычитает
калибровочный сдвиг `trim`.

### 4.4.1 Плеер и длинные файлы (Android 1.4.0)
- Android декодирует файл потоково в сегменты по 5 секунд (48 кГц, стерео, int16), каждый сегмент отображается через `mmap`.
  После готовности первого сегмента трек можно слушать, не дожидаясь полного декодирования. Размер Java-кучи не зависит от длины трека;
  PCM не требуется держать одним массивом или одним отображением. Поддержаны выходы кодека PCM 8/16/24/32 бит и float.
- Если декодер не успевает подготовить следующий участок, Server ставит общую шкалу на короткую паузу и возобновляет её,
  когда готов запас аудио. Перемотка ограничена уже подготовленной областью; L/R остаются на одной шкале. Процент подготовки виден на обоих экранах.
- На iOS эта итерация progressive-декодирование не меняет: декодер iOS пока загружает трек целиком перед началом воспроизведения.
- **Ресемплинг** — полифазный windowed‑sinc, 24 отвода (`StreamResampler`), вместо линейной интерполяции:
  для 15 кГц при 44,1→48 кГц искажения −113 дБ против −18 дБ у линейной.
- **Переход между треками без паузы**: после загрузки трека в фоне готовится следующий; держатся декодированными
  только предыдущий/текущий/следующий.
- **Пауза по общей шкале**: `timeline` той же эпохи с `stopFrame` = кадр через 150 мс — оба телефона замолкают на
  одном кадре с затуханием 5 мс; затем обычная эпоха «пауза». Play во время ожидания паузы отменяет её.
- **Без щелчков**: нарастание 5 мс после якоря (старт, seek, смена трека) и затухание 5 мс перед `stopFrame`.
- «Назад»: если трек играет > 3 с (или это первый трек) — в начало текущего, иначе предыдущий трек.

### 4.4.2 Очередь и плейлисты (Android 1.3.0)
- Заголовок очереди: «Очередь · N» и три значка — **Добавить музыку** (`playlist_add`), **Выбрать** (`checklist`,
  режим выбора с «Удалить (n)»), **Плейлисты** (`library_music`, нижняя панель). Значки — векторные пути Material Symbols.
- **Свайп влево** по треку удаляет его; 5 с доступна полоса «Удалено … · Вернуть» (и на Point). Удаление играющего
  трека включает следующий с тем же состоянием play/pause; если он был последним — остановка на первом треке.
- Треки больше **не копируются** в приложение: берётся постоянный доступ (`takePersistableUriPermission`) к выбранным
  файлам/папке, декодированный PCM кэшируется в `filesDir/audio_pcm` (очищается при запуске). Неиспользуемые
  разрешения (нет ни в очереди, ни в плейлистах) отпускаются — у Android лимит 128–512.
- **Плейлисты** — JSON в `filesDir/playlists` (`name`, `savedAt`, `tracks[{uri,title,artist}]`), только на Server.
  Сохранение с тем же названием перезаписывает плейлист. Открытие: «Заменить» или «Добавить» в конец; недоступные
  файлы пропускаются с сообщением. Долгое нажатие — переименовать / удалить.
- Название трека везде показывается как «Название - Исполнитель» (без исполнителя — только название);
  подпись «Локальная музыка» убрана. Команды `cmd`: `remove(ids[])`, `undoRemove`; в `state` — поле `undo`.

### 4.4.3 Передача файлов с Point (Android 1.4.0)
- Point может выбрать несколько аудиофайлов или папку, если Server тоже работает на Android; для передачи версия 1.4.0 нужна на обоих телефонах.
- Передача идёт порциями по 48 КиБ через дополнительный TCP JSON-обмен. На экранах обеих сторон отдельно показывается процент передачи;
  после приёма Server отображает подготовку аудио и использует обычный декодер и общую очередь.
- Ограничение: до 512 МиБ на файл и до 1 ГиБ на один выбор. Server принимает один файл за раз, проверяет размер, расширение,
  смещение каждого блока и сессионный токен. Данные сначала пишутся в `.part`, а незавершённый файл удаляется при отмене,
  ошибке или разрыве TCP. При переподключении текущая передача отменяется; на Point её можно остановить кнопкой «Отменить передачу».
- iOS не принимает файлы с Point. Android Point показывает явное сообщение, если второй телефон не Android.

### 4.5 Jitter buffer, потери, устаревшие пакеты (`PointReceiver`)
Кольцо на 2,7 с, адресуемое **абсолютным номером кадра** (каждая ячейка хранит тег кадра — чтение из аудиопотока без
блокировок). Пропуск в seq → NACK через 12 мс, повтор до 4 раз, Server перепосылает, если кадр ещё не проигран.
Учитываются: получено, восстановлено, потеряно, опоздавшие (пришли после воспроизведения), устаревшие (старая эпоха),
jitter по RFC 3550, underrun.

### 4.6 Акустическая калибровка (`CalibrationAnalyzer`)
Одинаковое время подачи PCM ≠ одновременный звук: у моделей разная задержка ЦАП/DSP/динамика. Калибровка:
1. Server включает микрофон (Android: `UNPROCESSED`/`VOICE_RECOGNITION`; iOS: `.playAndRecord` + `.measurement`, без AGC/AEC).
2. По общей шкале Point играет 6 **восходящих** чирпов (1,5→7,5 кГц, 21 мс) в 0,5 + k с, Server — 6 **нисходящих** в 1,0 + k с.
3. Взаимная корреляция (БПФ) находит моменты прихода каждого чирпа с субсэмпловой точностью.
4. `late_k = (приход_Point − приход_Server) − (ожид_Point − ожид_Server)`; абсолютное время записи и задержка микрофона
   сокращаются. Медиана по 6 парам, разброс (MAD) — оценка качества; > 3 мс → «повторите в тишине».
5. «Автокалибровка»: `trim_new = trim_old − late` (сохраняется в паре). «Только измерить»: показывает фактическое
   рассогласование L/R без изменений.

Ручной путь (если микрофон запрещён или «трудный» телефон): ползунок сдвига ±250 мс (шаг 0,5) + метроном в обоих каналах.

### 4.7 Жизненный цикл пары
```
IDLE ──invite──▶ INVITING ──accept──▶ PAIRED ◀──resume (без подтверждения)──┐
  ▲                 │                 │  обрыв TCP / нет данных 8 с          │
  │  reject/timeout │                 ▼                                      │
  └─────────────────┘            RECONNECTING ──оба телефона шлют resume ─────┘
IDLE ◀── bye / подтверждение на индикаторе пары (пара запоминается; «Забыть» — удаляет)
```
- При потере связи **Server продолжает играть** свою часть шкалы; Point замолкает. **Оба** телефона каждую секунду
  (после минуты — каждые 3 с) пробуют `resume`, попеременно по последнему известному адресу `lastHost:lastPort`
  (без mDNS — срабатывает сразу после разблокировки) и по адресу из Bonjour/NSD (если IP сменился).
  Встречные `resume` разрешаются как встречные приглашения: входящее принимает телефон с бо́льшим id, второй отвечает
  `reject: crossed` и ждёт `accept`. После `resume` Point заново синхронизирует часы (burst PING) и подхватывает
  воспроизведение **с текущего места**.
- `resume` принимается и когда получатель ещё считает связь живой (полуоткрытое TCP‑соединение после сна) —
  старое соединение заменяется, музыка не сбрасывается.
- Пока Server играет, Point раз в секунду передаёт возраст последнего принятого аудиопакета. Если пакеты не приходят
  или Server не знает UDP-адрес Point дольше 5 с, на обоих экранах появляется предупреждение; Server создаёт новый
  `sessionId`, сбрасывает UDP-адрес и отправляет новую сессию. Point сразу запускает PING-burst. Попытка повторяется
  не чаще раза в 5 с, TCP-пара и позиция трека сохраняются. Та же логика работает на Android и iOS.
- Возврат в приложение (разблокировка) и смена сети Wi‑Fi сразу запускают попытку, не дожидаясь таймаутов; если связь
  «молчит» > 4 с, соединение переоткрывается. Порт TCP‑сервера сохраняется между запусками, чтобы старый адрес оставался верным.
- **Автовосстановление** (фоновое, без диалога): пока пару не разорвали явно (подтверждение на индикаторе / `bye` / «Забыть»),
  при запуске и возврате в приложение телефон 30 с раз в 3 с тихо пробует `resume`. Экран остаётся обычным — можно
  сразу создать новую пару; входящее приглашение отменяет фоновое восстановление. Ответ `reject: unknown` (второй
  телефон забыл пару) выключает автовосстановление.
- Встречный `resume` отклоняется (`crossed`) только если наше исходящее соединение **уже установлено**; если оно
  ещё висит на старом адресе — принимаем входящее (раньше попытки могли бесконечно отклонять друг друга).
- iOS: P2P (AWDL) выключен — Android его не поддерживает, а iOS мог выбрать AWDL‑адрес и зависать на подключении.
  Android 14+: из адресов сервиса NSD выбирается IPv4.
- **Android без пары в фоне невидим.** Без foreground-сервиса Android замораживает процесс вскоре после ухода с экрана:
  TCP ещё принимается ядром, но ответа нет. Поэтому при `onStop` без пары снимается NSD-публикация и поиск,
  при возврате — включаются снова. В паре (и при переподключении) сервис держит процесс, публикация остаётся.
- **Приглашение**: получатель сразу отвечает `ringing` (показал диалог). Если сосед объявил TXT `ringing=1`, но за 8 с `ringing` не пришёл —
  «второй телефон не отвечает»; после `ringing` ждём подтверждения до 65 с. Без TXT `ringing=1` (старые Android и iOS) ждём до 65 с, даже без `ringing`.
  Повторный `ringing` не продлевает ожидание бесконечно. Подтверждается обработка приглашения приложением,
  а не фактическая отрисовка диалога на экране.
- NSD на Android: повтор публикации при отказе регистрации, пауза между снятием и повторной публикацией,
  без дубликатов в очереди resolve.
- Журнал подключения (последние 60 событий) — в «Диагностике» и на стартовом экране (кнопка «Журнал подключения»).
- Встречные приглашения (оба нажали одновременно) разрешаются детерминированно: уступает телефон с бо́льшим id.
- Телефон в паре отвечает на чужие приглашения `busy`.

## 6. Решения, принятые по умолчанию

1. **Транспорт — общая Wi‑Fi сеть** (или точка доступа одного из телефонов): единственный путь, работающий Android↔iPhone
   без специальных разрешений. Wi‑Fi Direct / Wi‑Fi Aware — кандидаты следующих версий.
2. **Стриминг PCM с Server** (а не «файл на обоих»): Point получает только свой канал, 96 КБ/с.
3. Пригласивший — Server и левый канал; каналы меняются кнопкой без пересоздания пары.
4. Громкость — цифровая в приложении (системную громкость iPhone нельзя менять программно). Системные кнопки
   громкости регулируют только свой телефон.
5. Калибровку выполняет микрофон **Server**; сдвиг применяется на Point (плавно, без щелчков); хранится в паре.
6. Прерывание на любом телефоне → пауза всей пары; автоматического возобновления нет (явное «Играть»).
7. Сохранённая пара доверенная (общий ключ `key`), повторное подключение — без подтверждения.
8. Исчезновение Point не останавливает музыку на Server; Point возвращается в текущую позицию.

## 8. Ограничения платформ и риски

- **iOS, наушники**: в категории `.playback` нельзя принудительно вывести звук на динамик — при подключении наушников/BT
  приложение показывает предупреждение. Android закрепляет вывод за встроенным динамиком (`setPreferredDevice`).
- **Точность «акустически»** зависит от расстояния между телефонами при калибровке (≈ 3 мс на метр) — поэтому калибровать рядом.
- **Гостевые/публичные Wi‑Fi** с изоляцией клиентов блокируют связь между телефонами — используйте домашнюю сеть или точку доступа.
- **Агрессивные оболочки Android** (Xiaomi, Huawei, Oppo) могут убивать фон даже при foreground‑сервисе — добавить SoundField
  в исключения батареи.
- **iOS в фоне без пары** приложение засыпает (это нормально); в паре аудиодвижок работает постоянно и держит сеть.
- Разрешения: iOS — локальная сеть (обязательно), микрофон (только калибровка); Android 13+ — уведомления (для фона), микрофон.

## 9. Чек‑лист ручного тестирования
1. Android↔Android, iPhone↔iPhone, Android↔iPhone: пара создаётся, на обоих видно L/R и роли; ожидаются
   `INVITE_ACCEPT`, `TCP_CONNECTED`, `PHASE`.
2. Play/Pause/seek/±10 с с Server и с Point — оба телефона реагируют одновременно; ожидаются `USER_COMMAND`,
   `CMD_APPLIED`, `CMD_RESULT_OBSERVED`.
3. Громкость: общая и по каналам с обоих телефонов, значения совпадают на экранах; ожидается `USER_COMMAND`.
4. «Поменять L/R» во время воспроизведения — каналы меняются за ~0,3 с; ожидаются `USER_COMMAND`, `CMD_APPLIED`.
5. Автокалибровка → «Только измерить» показывает |L/R| < 2 мс; метроном на слух — один щелчок; ожидаются
   `CALIBRATION_START`, `CALIBRATION_STAGE`, `CALIBRATION_END`.
6. Выключить экран на обоих на 5 минут — звук и синхронность сохраняются; ожидаются `APP_BACKGROUND`, `APP_FOREGROUND`
   и периодические снимки `HEALTH`.
7. Выключить Wi‑Fi на Point на 10 с и включить — пара восстанавливается сама, Point вступает в текущую позицию;
   ожидаются `LINK_ENDED`, `RECONNECT_START`, `RECONNECT_ATTEMPT_END`, `UDP_FIRST_PACKET`.
8. Входящий звонок на любом телефоне — пауза на обоих; ожидаются `AUDIO_FOCUS_CHANGE`, `USER_MESSAGE`, `USER_COMMAND`.
9. Нажать индикатор пары, подтвердить разрыв, затем нажать «Подключить» — пара восстанавливается без нового
   подтверждения на втором телефоне; ожидаются `USER_COMMAND`, `PHASE`, события переподключения.
10. Диагностика: RTT, jitter, потери, буфер ~350–400 мс, drift в пределах ±100 ppm, underrun = 0; ожидается
    обновление `HEALTH` и нет активных инцидентов.
11. Android: запустить длинный MP3 и убедиться, что воспроизведение начинается до завершения декодирования; при отставании
    декодера шкала должна буферизоваться и продолжаться без ухода L/R друг от друга. Проверить перемотку в готовую и неготовую области.
    Ожидаются `AUDIO_DECODE_START`, `AUDIO_DECODE_FIRST_AUDIO`, `AUDIO_DECODE_COMPLETE`; при нехватке буфера — `DECODE_LEAD_LOW`.
12. Android ↔ Android: добавить с Point несколько файлов и папку, дождаться прогресса передачи и увидеть файлы в очереди обоих телефонов.
    Ожидаются `FILE_TRANSFER_START`, `FILE_TRANSFER_PROGRESS`, `FILE_TRANSFER_COMPLETE`; при обрыве — `FILE_TRANSFER_ABORTED`.
13. Android ↔ iPhone: убедиться, что Point показывает сообщение о неподдерживаемой передаче; ожидается `FILE_TRANSFER_REJECTED`,
    а локальное добавление на Server должно работать.

14. Прервать отдельную передачу выходом из приложения или обрывом сети — неполный файл не должен попадать в очередь;
    ожидается `FILE_TRANSFER_ABORTED`.
15. Android: несколько раз разорвать/восстановить пару, подключить/отключить наушники и Bluetooth,
    вернуться после звонка или другого плеера и нажать «Играть». Оба телефона должны снова звучать;
    отдельно проверить длительное воспроизведение с выключенным экраном. Ожидаются `AUDIO_FOCUS_CHANGE`,
    `AUDIO_RECOVERY` при восстановлении выхода и переходы `APP_BACKGROUND`/`APP_FOREGROUND`.
16. Намеренно прервать UDP во время воспроизведения при сохранённом TCP и проверить, что предупреждение появляется,
    Server создаёт новую сессию, а звук возвращается без ручного разрыва пары. Ожидаются `AUDIO_SESSION_RENEW`,
    `UDP_FIRST_PACKET` и завершение кратковременного инцидента, если он успел сработать. Повторить на Android и iOS.
17. В Android debug-паре включить на Server «Остановить UDP-аудио»: TCP остаётся подключён, а в диагностике
    появляется `POINT_NO_PACKETS`; после выключения переключателя проверить `INCIDENT_END` в экспорте.
    Ожидаются `DEBUG_FAILURE_START` и `DEBUG_FAILURE_END`.
18. При воспроизведении отрезка с сигналом канала выше −50 дБFS включить на Point «Обнулить выход»: пакеты продолжают поступать,
    но ожидается `POINT_SILENT_OUTPUT`; после выключения проверить окончание инцидента.
    Ожидаются `DEBUG_FAILURE_START`, `INCIDENT_START`, `INCIDENT_END`, `DEBUG_FAILURE_END`.
19. Нажать «Здесь проблема» на одном Android-телефоне и проверить одинаковый `markId` в журналах обоих.
    Затем экспортировать с любой стороны: один файл должен содержать два журнала, сводку, состояния и чёрный ящик.
    Ожидаются `USER_MARK` на обоих устройствах и `BLACKBOX` в обоих журналах.
20. Если один телефон молчит при работающем управлении, записать его роль (Server/Point), модель и версию Android,
    показатели диагностики на обоих телефонах и лог `adb logcat -d -s SoundField AudioTrack`.
    Сообщение `Recreating audio output` означает попытку восстановления локального аудиовыхода.
    Реальное восстановление после сбоя драйвера требует проверки на устройстве; JVM-тесты проверяют
    частичные записи, недоступные/устаревшие таймстампы, underrun, переполнение счётчика и сброс тайминга.
21. На Android включить отладку «Остановить UDP-аудио» во время проигрывания: звук остаётся, путь аудио и часов становится TCP; ожидаются `AUDIO_PATH`, `CLOCK_PATH`, `START_WAIT`, нет `POINT_BUFFER_LOW`.
22. На Android выполнить seek и сменить трек: Point получает не менее 500 мс до старта либо Server начинает через 2 секунды; ожидается `START_WAIT` со статусом `ready` или `timeout`.
23. На паре Android + iOS или Android 1.4.2: возможности `tcpClock` и `tcpAudio` не согласованы, используется прежнее UDP-аудио и пара работает как раньше.
24. Оставить пару на паузе 10 минут, затем запустить: AudioTrack прекращает запись тишины через 5 секунд и просыпается при старте эпохи; `AUDIO_RECOVERY` не возникает.
25. Зафиксировать задержку heartbeat больше 5 секунд или оставить пару недоступной минуту: `PROCESS_FROZEN` содержит состояние до/после, диагностика показывает счётчик/сумму, а экран рекомендаций показывается не чаще раза в сутки.
